# [종결] 운영 DB 정리 — `sender = null` 채팅 메시지 삭제 (chatRoomId 58)

> **결과**: `chat_id = 513` 1건 삭제 완료. STOMP 스펙 수정·배포 완료. 웹 전송 재활성화.

## 0. 종결 요약

| 항목 | 결과 |
|---|---|
| 삭제 | `chat_id 513` **1건** (58번 방 81건 → 80건). 반응 참조 없어 연쇄 영향 없음 |
| 실제 원인 | **프론트 payload 문제가 아님** — `sender` 가 클라이언트 값을 그대로 저장하는 구조(사칭 가능 취약점)였고, 그 구멍이 NULL 로 드러난 것 |
| 서버 조치 | `sender` 를 JWT→프로필 닉네임으로 서버가 채우도록 변경. 발신자 미식별 메시지는 저장 거절 |
| 웹 조치 | 새 스펙으로 `buildPayload` 수정, 전송 재활성화 |

### ⚠️ 이 요청서의 위험했던 점 (기록용)

본문 §1 에 삭제 조건을 `sender IS NULL` 로 적었다. 실제 스키마에는 `user_id` 도
nullable 이고 **385건 중 381건(99%)이 NULL** 인데, 이건 오염이 아니라 컬럼을
나중에 추가하고 백필하지 않아 생긴 정상 과거 데이터였다.
"sender 관련 컬럼 NULL" 로 넓게 해석했다면 **서비스 채팅 이력 전체가 삭제될 뻔했다.**

→ 교훈: 확인할 수 없는 스키마에 대해 삭제 조건을 SQL 조건 형태로 적지 말 것.
   증상·시각·내용으로 특정하고, 범위 확정은 데이터를 볼 수 있는 쪽에 맡길 것.

## 2. 무슨 일이 있었나

웹에서 채팅 메시지 전송(STOMP) 기능을 구현하던 중, **발행 payload 형식을 확정하지 못한 상태에서 운영 서버에 시험 발행**했습니다.

보낸 payload:

```json
{ "roomId": 58, "messageType": "CHAT", "content": "안녕하세요" }
```

- 발행 목적지: `/stomp/chat.room.58`
- 연결: `wss://api.toronchul.app/prod/ws-stomp`, CONNECT 헤더 `Authorization: Bearer {accessToken}`

서버는 이 프레임을 **정상 수용**해 `/topic/room58` 로 브로드캐스트하고 DB 에 저장했습니다.
다만 payload 에 발신자 정보가 없었고 서버도 STOMP 세션에서 발신자를 채우지 않아,
**`sender` 가 `NULL` 인 메시지가 저장**됐습니다. 새로고침 후 REST 재조회에서도
`sender: null` 이 그대로 내려오는 것으로 저장 자체가 그렇게 된 것을 확인했습니다.

## 3. 현재 영향

- **운영 모바일 앱**: 해당 토론방(58) 진입 시 **무한로딩**. Flutter DTO 의 `sender` 가
  non-nullable 이라 JSON 파싱 단계에서 실패하는 것으로 **추정**합니다 (Flutter 코드 미확인).
  방 하나만 영향받는 점, 웹 시험 발행 직후 시작된 점이 정황상 일치합니다.
- **웹**: 렌더는 방어 처리(닉네임 폴백)로 크래시를 막아 둔 상태라 영향 없음.
- **웹 전송 기능**: 즉시 비활성화(`SEND_ENABLED = false`). 추가 오염 없음.

## 4. 백엔드에 함께 여쭙고 싶은 것

정리와 별개로, 재발 방지를 위해 아래를 확인하고 싶습니다.

1. **STOMP 발행 payload 의 정식 스펙** — 발신자를 어떻게 식별하나요?
   CONNECT 시 인증은 통과했는데 메시지에는 발신자가 붙지 않았습니다.
   payload 에 별도 필드가 필요한지, 세션 principal 에서 채워야 하는지 알고 싶습니다.
   (REST Swagger 에는 `@MessageMapping` DTO 가 노출되지 않아 확인이 불가능했습니다.)
2. **서버 측 검증** — 발신자를 식별할 수 없는 메시지는 저장 대신 ERROR 프레임으로
   거절해 주실 수 있을까요? 클라이언트 실수가 DB 오염으로 이어지지 않게 하는 안전망입니다.
3. **모바일 방어** — `sender` 등 optional 필드에 nullable 파싱을 넣어두면
   유사 상황에서 앱 전체가 막히는 것을 피할 수 있습니다.
   (Swagger 기준 `ChatMessageResponse` 는 `content` 만 required 입니다.)
4. **테스트 환경** — 운영 외에 검증용 토론방이나 dev 서버가 있으면 알려주세요.
   이번 건은 운영에서 시험한 것이 직접적인 원인이었습니다.

## 6. 확정된 STOMP 전송 스펙 (백엔드 회신)

```json
{
  "roomId": 58,
  "messageType": "CHAT",
  "content": "안녕하세요",
  "opinionType": "AGREE",
  "userCommunity": "에펨코리아"
}
```

- `sender` 는 **보내지 않는다** — 서버가 JWT → 프로필 닉네임으로 채운다. 보내도 무시·덮어쓰기.
- `opinionType` / `userCommunity` 는 아직 클라이언트 값 사용.
  - 웹 소스: `opinionType` = `RoomDetailResponse.opinion`, `userCommunity` = `MyProfile.community.name`
- destination `/stomp/chat.room.{roomId}`, CONNECT 헤더 `Authorization: Bearer {token}` (기존과 동일)
- 인증 정보/프로필이 없으면 저장하지 않고 거절.

### 남은 이슈 — 거절 시 무응답

백엔드 회신 §4-2: 거절은 예외 처리 경로라 **클라이언트에 ERROR 프레임이 가지 않을 수 있음**.
현재 웹은 `client.publish()` 성공(=브로커 전달)만 확인하고 입력창을 비우므로,
**서버가 저장을 거절해도 사용자에게는 전송된 것처럼 보인다**(메시지는 영영 안 뜸).

→ 백엔드가 제안한 "에러 피드백 별도 추가"를 **요청하는 편이 좋다.** 그전까지는
   전송 후 브로드캐스트 수신 여부로 확인할 수밖에 없다.
