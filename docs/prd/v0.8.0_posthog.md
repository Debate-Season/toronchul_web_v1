## 1. 배경 — 지금 우리는 아무것도 모른다

리포 전체에 계측 **코드**가 0건이다. gtag · GA · Sentry · Amplitude · Mixpanel 어느 것도 `src/` 에 없다. (`.env.example` 에 `NEXT_PUBLIC_AMPLITUDE_API_KEY` 만 남아 있는데 사용처는 0건 — 과거 검토의 잔재다. §9.3)

그 결과 v0.7.1 에서 IA 를 2단계로 줄이고(`4d3f438`) 화면을 크게 바꿨는데(`a5f3e87`) **나아졌는지 알 방법이 없다.** 프론트에서 에러가 나도 사용자가 말해주기 전까지 모른다.

v0.8.0 의 목표는 기능 추가가 아니라 **"다음 버전을 근거로 결정할 수 있는 상태"를 만드는 것**이다.

## 3. 확정 사실 — 실측으로 확인한 것

추측으로 정한 항목이 없도록, 결정의 근거를 남긴다.

### 3.1 App Router 페이지뷰는 **수동 처리가 필요 없다**

PostHog 웹 문서 요약은 "App Router 는 페이지뷰를 수동으로 잡아야 한다"고 안내하지만, **설치한 SDK 의 실제 타입 정의는 다르다**:

```
capture_pageview: boolean | 'history_change'
  - 'history_change': 최초 로드 + History API 변경(pushState, replaceState, popstate)에서 캡처
  @default true (또는 defaults 가 '2025-05-24' 이상이면 'history_change')
```
> 출처: `node_modules/@posthog/types/dist/posthog-config.d.ts` (posthog-js 1.418.1)

Next.js 클라이언트 내비게이션은 History API 를 쓰므로 **`defaults` 만 최신으로 두면 자동으로 잡힌다.** `usePathname` 수동 훅을 만들지 않는다.

> 부수 효과: `ThreadTabs` 는 `replace`(replaceState)를 쓴다 → **탭 전환마다 페이지뷰가 1건 잡힌다.** 주제별 조회수를 그대로 얻으므로 의도에 맞다.

### 3.2 `defaults` 는 `'2026-06-25'` 로 고정

타입에 정의된 값과 각 날짜가 켜는 동작:

| 값 | 켜지는 것 |
|---|---|
| `'2025-05-24'` | `capture_pageview` 기본이 `'history_change'` |
| `'2026-01-30'` | 외부 스크립트 주입 위치가 `head` — **SSR 하이드레이션 에러 회피** |
| `'2026-06-25'` | 리플레이 네트워크 바디 스트리밍 |
| `'2026-08-29'` | 크로스 서브도메인 쿠키 우선 |

`'2026-01-30'` 의 하이드레이션 회피가 Next.js 에 필요하므로 그 이상이어야 한다. 가장 최신(`'2026-08-29'`)은 **오늘(2026-08-19) 이후 날짜**이고 우리가 안 쓰는 크로스 서브도메인 동작이라 한 단계 아래인 `'2026-06-25'` 로 둔다.

### 3.3 백엔드는 user id 를 주지 않는다 — JWT `sub` 를 쓴다

운영 Swagger 실측:

```
LoginResponse   ["accessToken","refreshToken","socialType","profileStatus","termsStatus"]
ProfileResponse ["profileImage","nickname","gender","ageRange","socialType",
                 "community","residenceProvince","residenceDistrict",
                 "hometownProvince","hometownDistrict"]
```

**둘 다 id 필드가 없다.** 그런데 액세스 토큰은 JWT 이고 클레임이 `["sub","iat","exp","type","role"]` 이다 (브라우저 실측, `sub` 는 숫자 문자열).

→ **`sub` 를 distinct ID 로, `role` 을 person property 로 쓴다.** 백엔드 작업 없이 오늘 식별이 된다.

- 서명 검증은 하지 않는다. 분석용 식별자일 뿐 권한 판단이 아니다.
- ⚠️ **토큰 포맷에 결합된다.** 백엔드가 클레임을 바꾸면 식별이 조용히 끊긴다. 디코드는 전부 방어적으로 짜고(실패 시 `null`), **`LoginResponse` 에 `userId` 를 추가해달라고 백엔드에 요청**한다(§7-4).
- `role` 을 person property 로 두면 **내부 계정(ADMIN) 트래픽을 대시보드에서 제외**할 수 있다.

### 3.4 리버스 프록시 경로

PostHog 문서는 `/analytics`, `/tracking`, `/telemetry`, `/posthog` 같은 뻔한 경로를 쓰지 말라고 명시한다(차단기 규칙에 걸린다). 우리는 **`/relay`** 를 쓴다.

목적지 호스트(실측 확인):

| 리전 | 수집 | 정적 자산 |
|---|---|---|
| US | `us.i.posthog.com` | `us-assets.i.posthog.com` |
| EU | `eu.i.posthog.com` | `eu-assets.i.posthog.com` |

`skipTrailingSlashRedirect: true` 가 필요하다 — PostHog 수집 엔드포인트가 트레일링 슬래시를 쓰기 때문. **부수 효과**: `/foo/` → `/foo` 자동 리다이렉트가 사라진다. 우리 링크는 전부 슬래시 없이 생성되므로 실사용 영향은 없지만, 외부에서 슬래시를 붙여 들어오면 중복 URL 이 된다. 감수한다.

## 5. 이벤트 명세

이름은 **한 번 흩뿌리면 되돌리기 어렵다.** 여기서 확정하고, 코드에서는 판별 유니온으로 강제한다.

| 이벤트 | 속성 | 답하려는 질문 |
|---|---|---|
| `issue_viewed` | `issue_id` | 어떤 이슈가 실제로 읽히나 |
| `thread_opened` | `issue_id`, `thread_id` | 이슈 안에서 어느 주제로 들어가나 |
| `vote_cast` | `thread_id`, `opinion`, `changed` | 투표 전환율. 입장을 바꾸는가 |
| `message_sent` | `thread_id`, `opinion`, `length` | 읽기→쓰기 전환율 |
| `message_rejected` | `thread_id` | 서버 거절이 얼마나 잦은가 (`e2911a1` 로 알게 된 실패) |
| `login_started` | `provider` | 로그인 퍼널 진입 |
| `login_succeeded` | `provider`, `is_new_user` | 로그인 성공률·신규 비율 |
| `login_failed` | `provider`, `reason` | **어디서 깨지는가 — 지금 완전히 깜깜한 구간** |

핵심 퍼널: `issue_viewed → thread_opened → vote_cast / message_sent`
로그인 퍼널: `login_started → login_succeeded | login_failed`

> `$pageview` 는 SDK 가 자동 수집하므로 명세에 넣지 않는다.

## 6. 불문율과의 정합

| 불문율 | 처리 |
|---|---|
| **#2 `fetch` 직접호출 금지** | `apiFetch` 는 **우리 백엔드 envelope 전용** 규칙이다. PostHog SDK 는 자체 전송 계층을 갖는 서드파티이므로 대상이 아니다. 대신 **"PostHog 호출은 `src/lib/analytics/` 밖에서 하지 않는다"** 를 새 규칙으로 둔다 |
| **#3 `any` 금지** | 이벤트를 판별 유니온으로 정의해 이름·속성이 함께 검사된다. JWT 디코드는 `unknown` + narrowing |
| **#4 `_hasHydrated` 가드** | `identify()` 를 하이드레이션 전에 부르면 **로그인 사용자를 익명으로 잘못 식별**한다. `useAuthStore._hasHydrated` 를 기다린 뒤 호출 |
| **#5 TDS 는 leaf** | `De*` 컴포넌트에 트래킹을 넣지 않는다. 버튼은 `onClick` 을 props 로 받고 캡처는 호출부에서 |
| **#7 기능 간 교차 import** | `lib/analytics` 는 기능 디렉토리가 아니므로 어디서 불러도 무방 |

### 8.1 실제 키 투입 후 (2026-08-19)

US 프로젝트 키를 `.env.local` 에 넣고 재확인했다. dev 빌드는 `debug: true` 라
콘솔에 `send "<이벤트명>"` 이 찍혀 이름을 직접 읽을 수 있다.

- [x] **distinct ID 가 JWT `sub` 와 일치** — localStorage 의 `ph_*_posthog.distinct_id` 와 토큰 `sub` 대조, 일치. 익명 UUID 아님
- [x] `$identify` · `$set` 전송 확인
- [x] `History API monitoring enabled` — `capture_pageview: 'history_change'` 실제 활성
- [x] `$pageview` 가 이슈 진입 · 뒤로가기 · 토론방 진입 · 탭 전환 **각 1회**
- [x] `issue_viewed` · `thread_opened` 정상 전송
- [x] `vote_cast` · `message_sent` — **사용자가 직접 투표 3회·메시지 1건 수행하여 확인.** `vote_cast` 3건이 `POST /api/v1/room/vote` 3건(01:06:36 / 01:06:38 / 01:07:06)과 시각까지 1:1 로 일치 → 중복 아님, 실제 행동 그대로
- [ ] `message_rejected` — 미검증. 서버가 거절하는 상황을 인위로 만들어야 한다
- [ ] `login_failed` — 미검증. 인증 실패/취소를 인위로 만들어야 한다

### 8.1.1 로그인 플로우 실측 (2026-08-20)

사용자가 dev 서버에서 직접 로그아웃 → 카카오 재로그인. 콘솔 실측:

```
00:35:06  send "$set"
00:35:06  send "$pageview"        ← 콜백 페이지
00:35:06  send "login_succeeded"
00:35:06  send "$identify"
00:35:06  send "$pageview"        ← router.push 후 홈
00:35:12  send "$web_vitals"
```

- [x] `login_succeeded` — **1회.** 중복 없음
- [x] `$identify` — **1회**, 이후 `distinct_id = 9` = JWT `sub`, person property `role = ADMIN`
- [x] **로그아웃 시 `reset()`** — 간접 확증. `identifyUser` 는 `get_distinct_id() === sub` 면 조기 반환한다. 로그아웃 전 이미 `9` 였는데 재로그인에서 `$identify` 가 **나갔다**는 것은 그 사이에 ID 가 익명으로 초기화됐다는 뜻이다. `$device_id`(UUID) ≠ `distinct_id`(`9`) 도 일치하는 정황
- [x] `$pageview` 2건은 정상 — 콜백 페이지 1건 + `router.push` 후 목적지 1건
- [x] `login_started` — **콘솔 직접 관측은 불가.** `kauth.kakao.com` 으로 크로스 도메인 이동하면서 콘솔·네트워크 버퍼가 비워진다. 대신 전송 보장을 코드로 확인: `posthog-js` 는 POST 를 `keepalive: true` 로 보낸다(`dist/main.js`, ~51KB 미만 조건). **페이지 언로드 후에도 요청이 살아남는다** — `capture()` 직후 `location.href` 로 떠나도 유실되지 않는다. 최종 확인은 PostHog Activity 에서 `login_started` 존재 여부로

### 8.1.2 발견 — 콜백 URL 의 인가 코드가 PostHog 로 나간다 (미수정)

`$pageview` 의 `$current_url` 은 `location.href` 그대로다. OAuth 콜백 페이지에서
찍히는 값은 다음과 같다:

```
/oauth/callback/kakao?code=<인가코드>&state=<CSRF nonce>
```

즉 **인가 코드와 state 가 분석 이벤트에 실려 제3자(PostHog US)로 나가고 1년간
보관된다.** 코드는 그 시점에 이미 교환돼 재사용이 불가하고 state 도 소비된
뒤라 즉시 악용 가능한 값은 아니다. 그래도 자격증명을 분석 도구에 남기는 건
피해야 한다.

**수정 완료 (2026-08-20)** — `client.ts` 에 `before_send` 훅을 달아 전송 직전에
URL 속성에서 자격증명 파라미터를 지운다.

- 지우는 파라미터: `code` `state` `id_token` `access_token` `refresh_token` `token`
- 훑는 속성: `$current_url` `$referrer` `$initial_current_url` `$initial_referrer`
  - `$referrer` 가 필요한 이유 — 콜백 → 홈 이동에서 홈 페이지뷰의 referrer 가 곧 콜백 URL 이다
  - `$set` · `$set_once` 도 훑는다. 초기 URL 이 person 속성으로 따로 실린다
- **쿼리 전체를 날리지 않는다.** 우리 화면의 필터·정렬 파라미터까지 잃는다. 위 목록만 지운다
- URL 로 파싱되지 않는 값(`"$direct"` 등)이나 지울 게 없는 경우 원본 그대로 반환

처음에는 `sanitize_properties` 로 붙였으나 SDK 가 런타임에
`sanitize_properties is deprecated. Use before_send instead` 를 찍어 `before_send`
로 교체했다. 교체 후 경고 사라짐 확인.

### 8.2 발견 — 중복 전송 버그 (수정 완료)

`thread_opened` 가 내비게이션 1회당 **2번** 나갔다. 분석 이벤트의 중복은 곧
집계 오류라 그냥 둘 수 없다.

원인은 React StrictMode 의 개발 모드 이펙트 이중 실행으로 보였다 — `$pageview`
는 posthog 의 History 리스너가 보내서 1회인데, `useEffect` 로 보내는 우리
이벤트만 2회였다. 정황은 맞지만 **StrictMode 라고 단정하고 "프로덕션은
괜찮다"로 넘기지 않았다.** 재마운트·리렌더로도 같은 일이 생길 수 있다.

→ `useRef` 로 마지막 전송 키(`issueId:threadId`)를 들고 같은 값이면 건너뛴다.
원인을 가리지 않고 값 기준으로 막으므로 StrictMode 든 재마운트든 안전하다.
`issue_viewed` 도 같은 구조라 함께 고쳤다.

StrictMode 가 켜진 dev(가장 가혹한 조건)에서 재확인 — 4번의 내비게이션 모두
정확히 1회씩.

### 8.3 발견 — 우리가 정하지 않은 수집 2건 · dev 재초기화

서버 측 원격 설정으로 켜지는 것들이라 코드에 안 보인다.

| 항목 | 상태 | 판단 |

### 9.2 구현 중 정한 것

1. **키가 없으면 전체가 no-op.** `initAnalytics()` 가 그냥 반환하고 `capture`·
   `identify` 도 `initialized` 가드에 막힌다. 로컬·프리뷰에서 계측 없이 돌릴 수
   있고, 키 주입을 잊은 채 배포해도 앱이 죽지 않는다.

2. **`reset()` 은 로그아웃 "전환"에서만.** 비로그인 렌더마다 부르면 익명
   방문자의 distinct ID 가 매번 새로 발급돼 한 사람이 여러 명으로 세어진다.
   `wasLoginRef` 로 전환을 감지한다.

3. **본문을 절대 싣지 않는다.** `message_sent` 는 길이만, `message_rejected` 는
   빈도만 보낸다. 발언 내용은 정치적 견해에 해당한다(ideation §6.1 과 같은 이유).

4. **로그인 실패 사유는 우리가 정한 분류.** 서버·SDK 문구를 그대로 실으면
   백엔드가 문구를 바꿀 때 집계가 갈라진다. 카카오는 토큰 교환 실패
   (`token_exchange`)와 백엔드 거절(`login_api`)을 `stage` 변수로 구분한다 —
   대응이 전혀 다른 사고다.

### 8.4 관찰 — dev 에서 posthog 가 여러 번 초기화된다

한 세션에서 `Initializing extensions` + `Starting in debug mode` 가 3회 찍혔다.
`client.ts` 의 `initialized` 플래그는 모듈 수준 변수라 **Fast Refresh 가 모듈을
다시 평가하면 초기화된다.** 실제로 재초기화 시각이 소스 파일을 수정한 직후와
겹친다.

**이벤트 중복으로 이어지지는 않았다** — `vote_cast` 3건이 투표 API 3건과 1:1 로
일치한다. 프로덕션은 모듈을 다시 평가하지 않으므로 해당 없음. 기록만 남긴다.
