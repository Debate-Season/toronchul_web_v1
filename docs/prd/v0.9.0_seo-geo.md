## 1. 배경 — 지금 우리는 검색에 존재하지 않는다

측정부터 했다. 2026-08-20, Googlebot User-Agent 로 실서비스 이슈 상세를 요청한 결과다.

```bash
curl -A "Mozilla/5.0 (compatible; Googlebot/2.1; +http://www.google.com/bot.html)" \
     https://toronchul.app/issue/8/도널드-트럼프-2기-행정부
```

| 항목 | 실측값 |
|---|---|
| HTTP 상태 | 200 |
| 응답 크기 | 17,645 bytes |
| **스크립트·스타일 제거 후 본문 텍스트** | **30자** — `"토론철 토론철 홈 이슈맵 앱 다운로드 실시간 핫한 토론"` |
| `<title>` | `토론철` (전 페이지 동일) |
| `<meta name="description">` | `토론철 - 토론 플랫폼` (전 페이지 동일) |
| `<link rel="canonical">` | 없음 |
| JSON-LD | 없음 |
| `/robots.txt` | **404** |
| `/sitemap.xml` | **404** |

17KB 를 받아서 30자를 읽는다. 그 30자는 전역 네비게이션이고, 이슈 제목조차 들어 있지 않다.

원인은 단순하다. **색인 대상 4개 라우트가 전부 `"use client"`** 다.

```
src/app/issue/[id]/page.tsx                                  "use client"
src/app/issue/[id]/[slug]/page.tsx                           "use client"
src/app/issue/[id]/[slug]/[threadId]/[threadSlug]/page.tsx   "use client"
src/app/page.tsx                                             "use client"
src/app/map/page.tsx                                         "use client"
```

`src/lib/seo.ts` · `src/app/robots.ts` · `src/app/sitemap.ts` 는 **존재하지 않는다.**

> **2026-09-01 재측정 — 본문 30자, robots·sitemap 404, `/issue/8`·`/issue/8/틀린슬러그`·`/issue/abc/x` 전부 200. 위 표에서 바뀐 것이 없다.**
>
> 그 사이 `layout.tsx` 에 OG·twitter 메타는 들어갔다(응답 17,645 → 23,388 bytes). 다만 `title.template`·`robots`·Organization JSON-LD 는 아직 없고, 도메인이 `const SITE_URL` 로컬 선언으로 하드코딩돼 있다(`layout.tsx:6`) — §6.1 위반이다. **크롤러가 읽는 본문은 30자 그대로다.**
>
> **2026-10-18 재측정 — 여전히 같다.** robots·sitemap 404, `<title>토론철</title>`, canonical·JSON-LD 없음. 바뀐 것은 Naver 소유확인 파일(`public/naver*.html`, 200) 하나다. 위키 게시본 0건, 채팅 조회 401 도 그대로다.

즉 현재 상태는 "SEO 가 약하다" 가 아니라 **"SEO 가 0"** 이다. 이 사실에는 뒤집어 볼 면이 있다 — §3.1.

## 2. 목표

토론철의 4개 엔티티가 **각각 독립된 상세 페이지로** 일반 검색(Google·Naver·Bing)과 생성형 AI 검색(ChatGPT Search·Perplexity·Claude·Gemini·AI Overviews)에 잡히게 한다.

| 엔티티 | 페이지의 핵심 콘텐츠 | 권위의 원천 |
|---|---|---|
| **이슈** | 이슈위키(개요·배경) + 사건 타임라인 | 나무위키형 레퍼런스 문서 |
| **사건** | 실시간성(언제 무슨 일이) + 맥락 설명(왜 중요한가) | 최신성 + 해설 |
| **토론** (주제별) | 채팅 내역 기반의 토론 진행 경과 | 1차 사료 — 다른 데 없는 원본 데이터 |
| **AI 기사** | 토론철이 생성한 기사 본문 | 자체 발행 콘텐츠 |

레퍼런스 모델은 **나무위키**다. 나무위키가 검색을 지배하는 이유는 백링크가 아니라 구조다 — 하나의 주제에 하나의 URL, 그 URL 이 그 주제에 대해 인터넷에서 가장 긴 글, 목차로 쪼개져 부분 인용이 쉬움, 문서가 계속 갱신됨. 토론철은 여기에 **나무위키가 못 가진 것** 을 더한다: 그 주제에 대해 실제 사람들이 찬반으로 나뉘어 나눈 대화 원문.

> **GEO 관점에서 이게 왜 결정적인가** — LLM 은 "3대 특검이 뭔가"는 나무위키에서 답할 수 있다. 하지만 **"3대 특검에 대한 여론이 어떻게 갈리나"** 는 답할 소스가 없다. 그 질문의 유일한 1차 사료가 되는 것이 토론철의 GEO 전략이다.

## 3. 확정 사실

### 3.1 URL 은 지금 한 번만 바꾼다

> **2026-10-19 정정** — 최초 작성 시 "색인 0개" 로 봤으나, **현행 `/issue/{b36}/{slug}` 가 이미 운영 배포·색인돼 있다**(사용자 확인). 따라서 스킴 변경은 공짜가 아니라 **영구 308 이전**이다(§4.3e).

그래도 지금 바꾸는 게 맞다. 색인 규모가 작고(이슈 17·스레드 ~30), 사건·AI 기사로 URL 이 대량으로 늘어나기 **전**이다. 이전 비용은 URL 수에 비례하고, 한 번 정한 스킴은 이후 모든 신규 URL 에 적용된다. **두 번째 변경은 없다** — 이번 이전에서 레거시 규칙을 영구히 유지하고, 새 스킴은 바꾸지 않는다.

따라서 v0.9.0 은 "메타태그를 붙이는 작업"이 아니라 **URL 스킴 확정·이전 작업** 이 먼저다. (§4)

### 3.2 SSR 에 필요한 API 는 대부분 인증이 필요 없다

Swagger(`https://toronchul.app/prod/v3/api-docs`)와 실 curl 로 확인했다.

| 엔드포인트 | 인증 | 실측 | 용도 |
|---|---|---|---|
| `GET /api/v2/wiki?issue-id=N` | **불필요** | 200 | 이슈위키 본문(Markdown) |
| `GET /api/v2/room?issue-id=N` | **불필요** | 200 | 컨테이너 방 + 스레드 목록 |
| `GET /api/v1/users/home` | **불필요** | 200, 이슈 17건 | 사이트맵 이슈 목록 |
| `GET /api/v1/issue-map` | **불필요** | 200 | 이슈 목록(페이지네이션) |
| `GET /api/v1/issue?issue-id=N` | Swagger 상 JWT | **200 (익명)** | 이슈 상세 + 커뮤니티 분포 |
| `GET /api/v1/chat/rooms/{roomId}/messages` | **JWT 필수** | **401 MISSING_ACCESS_TOKEN** | **채팅 내역 — 토론 페이지 본문** |

**서버 컴포넌트에서 토큰 없이 호출하면 이슈 페이지는 오늘 당장 SSR 이 가능하다.** 반면 토론 페이지의 핵심 콘텐츠인 채팅 내역은 401 이라 **크롤러에게 보여줄 방법이 현재 없다.** → §7-1 백엔드 요청.

> `apiFetch` 는 401 이면 `@/lib/auth/logout` 을 동적 import 한다(브라우저 전용 코드). 다만 그 분기는 `res.status === 401 && token` 조건이라 **토큰 없이 부르는 SSR 경로에서는 타지 않는다.** SSR 호출은 반드시 토큰 없이 한다.

### 3.3 이 프로젝트는 pSEO 가 아니다 — 참고 문서를 그대로 쓰면 안 된다

`docs/ideation/*` 는 700만+ 페이지 규모 프로그래매틱 SEO 프로젝트의 문서다. 토론철의 현재 색인 대상은 다음과 같다.

```
이슈 17개 · 스레드 ~30개 · 정적 페이지 ~3개  →  총 50개 남짓
```

| 참고 문서의 전제 | 토론철에서의 실제 |
|---|---|
| 크롤 버짓 보호가 최우선 | **무관.** 50개 URL 은 Googlebot 이 한 번에 다 돈다 |
| Thin Content 임계값·경고 배너 정책 | **다른 문제다.** 우리는 표본이 작은 게 아니라 **본문이 아예 없다** |
| 사이트맵 40,000 URL 분할 · OOM · lazy 로딩 | 불필요. 단일 `sitemap.xml` 로 충분 |
| AWS WAF Bot Control 연동 | 인프라가 다르다(Vercel). 해당 없음 |
| IndexNow 대량 제출 | 후순위. 갱신 빈도가 낮다 |
| Phase 별 색인율 70% 게이팅 | 무의미. 전량 색인이 기본 기대치 |

> **단, 이 숫자는 출발점이다.** 이슈·사건·토론 주제·자체 생성 기사가 모두 대량으로 늘어나는 것이 전제다(2026-10-19 결정). 그래서 **URL 스킴은 대규모를 기준으로 정하고**(§4.3b·c), 크롤 버짓·사이트맵 분할 같은 운영 대응은 규모가 실제로 올 때 켠다(§6.2).

**가져올 것은 원칙이고, 버릴 것은 규모 대응이다.** 가져오는 것: canonical 단일 출처 아키텍처, `lastmod` 는 실제 데이터 갱신일만, noindex↔sitemap 동기화 불변, JSON-LD 는 화면 콘텐츠와 일치.

> **GEO 3축(엔티티 명확성·인용 가능성·사실 밀도)과 AI 봇 3계층은 참고 문서에서 그대로 가져오지 않는다.** 2026-08-21 리서치(`docs/ideation/seo-geo-skill-research.md`)에서 근거가 바뀌었다 — GEO 기법은 Princeton GEO 논문의 실측 순위로 대체하고, AI 봇 차단은 GEO 레버가 아니라 라이선스 결정으로 재분류했다. §6.3 및 스킬의 `references/{geo-evidence,crawler-policy}.md` 를 본다.

우리 고유의 문제는 정반대다: **URL 스킴 · 페이지당 콘텐츠 깊이 · 대량 생성 콘텐츠(사건·AI 기사)의 품질 관리.**

### 3.4 "사건"과 "AI 기사"는 아직 백엔드에 없다

Swagger 전수 확인 결과:

- **사건** — 해당 엔드포인트·스키마 없음. `GET /api/v1/lives`·`/api/v1/live/{id}` 는 이름이 비슷하지만 **v0.6.0 의 YouTube 라이브**(`YoutubeLiveDto: id, title, supplier, videoId, category, createAt, src`)다. 사건이 아니다.
- **AI 기사** — 없음. `GET /api/v1/home/media` 는 외부 매체 큐레이션(`MediaResponse: supplier, url, src, type, media`)이다. 자체 기사가 아니다.
- **이슈위키** — **있다.** `GET /api/v2/wiki` + 관리자 생성/게시 플로(`/api/v1/admin/wiki/{generate,publish,revisions}`)까지 완비. 다만 실측상 **게시본이 아직 0건**(issue 8·15·20 모두 `status: null, content: null`).

**불문율 #1(필드 조작 금지)에 따라 없는 DTO 를 만들지 않는다.** v0.9.0 은 이슈·토론 2종을 실제로 구현하고, 사건·뉴스는 **URL 자리와 스키마 계약만 예약**한다. (§6)

## 4. URL 전략 (이 PRD 의 핵심)

### 4.1 현재 스킴의 문제

`src/lib/slug.ts`:

```ts
export function issueHref(issueId: number, title: string): string {
  return `/issue/${toBase36(issueId)}/${toSlug(title)}`;
}
// threadHref → /issue/{b36}/{slug}/{threadB36}/{threadSlug}
```

| # | 문제 | 구체 |
|---|---|---|
| 1 | **같은 문서에 URL 이 2개** | `/issue/8` 과 `/issue/8/도널드-트럼프-2기-행정부` 가 **둘 다 200**. 중복 콘텐츠 |
| 2 | **slug 가 무한한 변형을 만든다** | 잘못된 slug 로 들어와도 그대로 200. 제목이 바뀌면 URL 도 바뀐다 |
| 3 | **한글 slug 의 인코딩 비용** | 공유하면 한 글자가 9바이트(`도` → `%EB%8F%84`)로 늘어난다. NFC/NFD·퍼센트 인코딩·`params` 디코딩 중 하나라도 어긋나면 정식형 판정이 깨져 **301 루프**가 난다 |
| 4 | **`fromBase36` 이 조용히 실패한다** | `parseInt("도널드", 36)` → `NaN`. 404 가 아니라 깨진 렌더. 대문자·선행 0 별칭도 그대로 200 |
| 5 | **토론이 이슈 아래 4단으로 묶여 있다** | 토론 하나에 세그먼트 4개. 부모 이슈 id 가 틀려도 검증하지 않는다 |
| 6 | **사건/기사 자리가 없다** | 목표 엔티티 4종 중 2종의 경로가 미정 |

### 4.2 확정 스킴

```
/                  홈
/map               이슈맵
/issue/{b36}       이슈 상세
/event/{b36}       사건 상세       ← 예약
/debate/{b36}      토론 상세
/article/{b36}     AI 기사         ← 예약
```

`{b36}` = 백엔드 정수 id 의 **소문자 base36**. 언어 접두어는 없다(§4.3f, §5.6).

```
/issue/8           이슈 8   (도널드 트럼프 2기 행정부)
/issue/k           이슈 20  (3대 특검)
/debate/1p         토론 61  (미국은 관세전쟁을 중단해야 하는가?)
/debate/22         토론 74
```

### 4.3 설계 근거

**(a) 슬러그를 넣지 않는다 — 정체성은 id 뿐**

2026-10-19 에 8개 서비스의 공식 문서를 다시 확인했다. 원문 인용·출처는 `.claude/skills/seo-geo/references/url-evidence.md`.

| 서비스 | 공식 입장 요약 |
|---|---|
| Google 검색 | URL 경로의 키워드는 순위에 **"거의 영향이 없다"**(브레드크럼 표시 외). 다만 **"랜덤 식별자만 있는 URL 은 사용자에게 덜 유용"**, 브레드크럼은 **"URL 속 단어로 자동 학습"** |
| Bing | ⚠(스니펫 확인) 중복 URL 은 그라운딩·인용 URL 선택 **신뢰도를 깎는다**. 슬러그 키워드 규칙은 없다 |
| Naver | 사용자·로봇이 쉽게 해석하는 URL, **파라미터 최소화**, **소문자**. 한글 URL·ID 형식 언급 없음 |
| Gemini · AI Overviews | Google 색인을 그대로 쓴다. **"추가 요건·특별한 최적화 불필요"** |
| ChatGPT · Claude · Perplexity | 크롤러 허용 여부만 문서화. **URL·슬러그 언급 없음** |

**슬러그가 순위에 영향을 준다고 명시한 곳은 없다.** 반대로 Google 과 Naver 는 "읽을 수 있는 URL" 을 권장한다 — 근거는 순위가 아니라 사용자 이해다. 이 권장에서 벗어나는 대가로 다음을 얻는다.

- 정식형이 **구조적으로 하나뿐**이다. 변형이 생길 수 없다(문제 1·2 소멸)
- 제목이 바뀌어도 301 이 필요 없다
- 인코딩·정규화 루프가 원천적으로 없다(문제 3 소멸)
- 공유 URL 이 짧다(카카오톡·메신저 복사 시 `%EB…` 없음)

**대가를 메우는 장치** — Google 이 URL 단어로 학습하던 브레드크럼을 **`BreadcrumbList` JSON-LD 로 직접 준다**(모든 상세 페이지 필수). 제목·설명은 `<title>`·`description`·H1 이 전달한다.

**(b) base36 — 대량 엔티티를 전제로 한다**

- 이슈·사건·토론·기사가 모두 대량으로 늘어나는 것이 전제다(§3.3). 길이 절감은 규모가 커질수록 커진다 — 100만 = `1000000`(7자) → `lfls`(4자), 약 35%
- **소문자 고정.** Google 은 URL 대소문자를 구분하고, Naver 는 소문자를 권장한다. 대소문자를 섞는 **base62 는 쓰지 않는다**
- **은닉 수단이 아니다.** base36 은 누구나 디코딩할 수 있고 순서도 그대로다. 개수·순서를 감추는 용도로 쓰지 않는다
- **현재 인코딩과 같다.** 기존 공유 링크의 id 세그먼트를 그대로 재사용하므로 레거시 이전에 변환이 필요 없다(§4.3e)
- 대가: 사람과 로그가 읽기 어렵다. 로그·에러 리포트에는 10진수 id 를 병기한다

**(c) 엔티티별 평평한 최상위 디렉터리**

| 후보 | 채택 | 이유 |
|---|---|---|
| 중첩 `/issue/{b36}/debate/{b36}` | ✗ | 부모가 틀린 URL(`/issue/a/debate/22`)도 200 이 되지 않도록 **매번 부모를 검증하고 리다이렉트**해야 한다. 놓치면 Bing 이 말하는 중복 URL 이 된다. 토론이 다른 이슈로 옮겨가면 URL 이 바뀐다 |
| **평평 `/debate/{b36}`** | **✓** | URL 하나 = 엔티티 하나. 상위 관계는 `BreadcrumbList`·`isPartOf` 로 표현한다 |

엔티티 종류마다 디렉터리를 나누는 이유: Google 은 **"수천 개 URL 을 넘으면 디렉터리 구조가 크롤링·색인에 영향을 준다"**, 디렉터리별로 **갱신 빈도를 학습**한다고 한다. 사건·기사(자주 바뀜)와 이슈(드물게 바뀜)를 디렉터리로 분리해 두면 그 학습이 정확해진다.

> **선결 조건** — `GET /api/v1/room?chatroom-id=N` 은 익명 200 이지만 응답(`ChatRoomResponse`)에 **`issueId` 가 없다**(2026-10-19 실측). 평평한 URL 에서는 스레드 id 만으로 상위 이슈와 컨테이너 방(`containerRoomId`, 채팅 조회 경로에 필요)을 알아내야 한다. 또 이 엔드포인트는 컨테이너 방 id(예: 155)도 200 으로 돌려주므로, **스레드가 아닌 id 를 404 로 거를 방법도 필요하다.** → §7-13
>
> 백엔드가 이를 줄 수 없으면 대안은 중첩 스킴 + 부모 검증 리다이렉트다. 그 경우 이 절을 다시 연다.

**(d) 정식형 판정 규칙**

| 요청 | 응답 |
|---|---|
| `/issue/q` | 200 (정식형) |
| `/issue/Q` | **308** → `/issue/q` |
| `/issue/0q` · `/issue/q-x` · `/issue/한글` | **404** (비정식 별칭·잘못된 문자) |
| 존재하지 않는 id | **404** |
| `/issue/q?utm_source=…` | 200, canonical 은 쿼리 없는 형 |

판정 순서:

1. 세그먼트가 `^[0-9a-z]+$`(대소문자 무시) 아니면 → 404
2. 소문자화한 값 `s` 에 대해 `toBase36(fromBase36(s)) !== s` 이면 → 404. 선행 0 같은 **별칭을 리다이렉트가 아니라 404 로 막는다** — 별칭에 301 을 주면 무한한 유효 URL 이 생긴다
3. 원래 세그먼트에 대문자가 있었으면 → 308 → 소문자형
4. 백엔드 조회가 404 면 → `notFound()`

> Next.js 의 `permanentRedirect()` 와 `redirects()` 의 `permanent: true` 는 **308** 을 낸다. Google 은 301·308 을 동일하게 영구 리다이렉트로 처리한다.

**(e) 레거시 URL 이전 — 이미 퍼진 링크를 살린다**

색인된 페이지는 0개지만, **카카오톡·앱으로 공유된 링크는 이미 퍼져 있다.**

| 레거시 | 응답 |
|---|---|
| `/issue/{b36}` (기존 id 전용 경로) | **그대로 정식형** — 변경 없음 |
| `/issue/{b36}/{slug}` | **308** → `/issue/{b36}` |
| `/issue/{b36}/{slug}/{threadB36}/{threadSlug}` | **308** → `/debate/{threadB36}` |

- id 인코딩이 같으므로 **세그먼트를 그대로 옮기기만 하면 된다.** `next.config` 의 `redirects()` 패턴으로 처리할 수 있다
- 레거시 경로는 **영구 유지**한다. 색인된 URL 과 공유된 링크는 회수할 수 없다
- 모바일 앱은 웹 URL 을 만들지 않는다(공유 기능·웹 링크 없음, 2026-10-19 `toronchul_mobile` 확인) → §7-12 해소

**진행 상태 (2026-10-19)**

| 이전 | 상태 |
|---|---|
| `/issue/{b36}/{slug}` → `/issue/{b36}` | **구현** — `next.config.ts` `redirects()` 308 + `src/app/issue/[id]/page.tsx` 정식형 판정. 로컬 `next start` 로 §9.1 매트릭스 확인 |
| 토론 4단 경로 → `/debate/{b36}` | **구현** — `next.config.ts` 308 + `src/app/debate/[id]/page.tsx`(스레드 단건 조회로 `issueId` 확보, CONTAINER·HIDDEN·DELETED·없는 id 404). 백엔드 PR #214 배포 후 실 curl 로 필드 확인. 로컬 `next start` 로 §9.1 매트릭스 확인 |

배포 후 할 일: GSC·Bing 에 새 URL 로 sitemap 제출(§10 5단계) — 옛 URL 의 재크롤이 308 을 빨리 발견하게 한다.

**(f) URL 에 언어를 넣지 않는다**

원문 단일 원칙(§5.6)에 따라 **로케일 접두어(`/en/…`)·`?lang=`·hreflang 을 쓰지 않는다.**

- 결과적으로 **로케일 처리용 `proxy.ts`(Next 16, 구 `middleware`)가 필요 없다.** `/oauth/callback/kakao`·`/api/auth/apple/callback` 에 미들웨어가 개입해 운영 중인 로그인과 모바일 앱 호환을 깨뜨릴 위험이 원천적으로 사라진다
- **다시 여는 조건** — "영어 검색·영어 AI 답변에 노출" 이 목표가 되면 그때는 **별도 URL 이 필수**다(Googlebot 은 `Accept-Language` 없이 크롤링한다 — §5.6). 한국어 URL 은 접두어가 없으므로 `/en/…` 을 추가해도 **기존 URL 은 하나도 바뀌지 않는다.** 그 결정은 새 PRD 로 한다

## 5. 페이지별 콘텐츠 · 스키마 설계

### 5.1 이슈 상세 — 나무위키형 레퍼런스

**본문 구성(서버 렌더 필수)**

1. H1: 이슈 제목
2. **정의 문단** — 이 이슈가 무엇인지 1~2문장. GEO 인용 가능성의 핵심(§9.2)
3. **이슈위키 본문** — `GET /api/v2/wiki` 의 Markdown. 목차(H2/H3)를 살려 렌더. 부분 인용이 가능해야 한다
4. **사건 타임라인** — 시간 역순 목록 (백엔드 준비 후)
5. **토론 목록** — 스레드별 제목 + 찬반 수. 각각 토론 상세로 링크
6. **참여 커뮤니티 분포** — `IssueDetailResponse.map` (`Record<string, number>`). 구체 수치 = 사실 밀도

> **위키 게시본이 없을 때**(현재 전 이슈) — `content: null` 이면 위키 섹션을 생략하고 토론 목록·타임라인으로 페이지를 구성한다. **`noindex` 를 걸지 않는다.** 참고 문서 §8 의 교훈: 임계값 기반 noindex 는 데이터가 채워질 때마다 색인이 켜졌다 꺼지는 flapping 을 일으킨다.

**JSON-LD**

```
Article
  @id            {SITE_URL}/issue/8#article
  headline       이슈 제목
  about          Thing { @id, name, sameAs: [위키백과·나무위키 URL] }   ← GEO 핵심
  datePublished  issue.createdAt
  dateModified   wiki.updatedAt ?? 최신 스레드 활동 시각
  publisher      Organization(토론철)
  mainEntityOfPage / isPartOf
BreadcrumbList   홈 › 이슈 › {제목}
ItemList         사건 타임라인 (ListItem → 사건 상세 URL)
```

> **`about.sameAs` 가 왜 결정적인가** — GEO 3축의 "엔티티 명확성"을 브랜드가 아니라 **주제** 에 적용하는 것이다. `sameAs: ["https://ko.wikipedia.org/wiki/..."]` 는 LLM 에게 "이 페이지의 '3대 특검' 은 네가 이미 아는 그 3대 특검이다" 라고 말한다. 이게 있어야 토론철 페이지가 기존 지식 그래프에 **접속**한다. 외부 URL 은 추측 금지 — 실제 확인된 것만 넣는다.

### 5.2 사건 상세 — 실시간성 + 맥락 (예약)

**본문**: 발생 시각 → 무슨 일이 있었는지(사실) → 왜 중요한지(맥락) → 상위 이슈 링크 → 관련 토론 링크.

**JSON-LD**: `NewsArticle` + `BreadcrumbList` + `isPartOf` → 이슈.

> **`Event` 를 쓰지 않는 이유** — schema.org 의 `Event` 는 "예정된 행사"(공연·컨퍼런스)이고 Google 의 Event 리치 결과는 `location`·`startDate` 를 요구한다. 뉴스적 "사건"에 붙이면 규격 위반으로 GSC 오류가 난다. `NewsArticle` 의 `datePublished`(최초 보도) / `dateModified`(최신 갱신)가 실시간성을 표현하는 정확한 수단이다.

### 5.3 토론 상세 — 채팅 기반 진행 경과

**본문**: H1 스레드 제목 → 찬반 현황(`agreeCount`/`disagreeCount`, 총 참여 수) → **진행 경과 요약** → 대표 발언(찬성/반대 각각) → 전체 채팅 내역 → 상위 이슈 링크.

**JSON-LD**

```
DiscussionForumPosting
  @id                    {SITE_URL}/debate/1p#thread
  headline               스레드 제목
  datePublished / dateModified
  interactionStatistic   InteractionCounter × N (찬성 수 / 반대 수 / 발언 수)
  comment                Comment[] (작성자는 닉네임, 본문, 시각)
  isPartOf               이슈 Article  ← URL 이 평평하므로 상위 관계는 여기와 BreadcrumbList 가 유일한 표현이다
BreadcrumbList   홈 › {이슈 제목} › {토론 제목}
```

`DiscussionForumPosting` 은 Google 이 "Discussions and forums" 리치 결과를 위해 지정한 타입이다. 레딧·커뮤니티가 검색 상위를 먹는 그 자리다. 우리 콘텐츠 형태와 정확히 일치한다.

> **두 개의 선결 조건**
> 1. **채팅 조회 API 가 401 이다.** 서버에서 못 읽으면 본문이 없다 → §7-1
> 2. **개인정보 문제.** 채팅에는 닉네임·소속 커뮤니티·의견이 붙는다. 이걸 검색엔진에 공개 색인시키려면 이용약관·개인정보처리방침에 "게시물의 공개 및 검색엔진 색인" 조항이 있어야 하고, 사용자가 사전에 인지해야 한다 → §7-2

### 5.4 AI 기사 `/article/{b36}` (예약)

> **웹 구현은 `v1.1.0_toronchul-article.md`** (2026-10-19). 아래 발행 게이트는 그 문서의 착수 조건이다.

**JSON-LD**: `NewsArticle` + `BreadcrumbList` + `about` → 관련 이슈.

> **여기에는 실질적 리스크가 있고, 그냥 넘기지 않는다.** Google 스팸 정책(2024-03 도입, developers.google.com/search/docs/essentials/spam-policies)의 **"scaled content abuse"** 는 AI 생성 자체를 벌하지 않는다. 대상은 *"검색 순위를 조작할 목적으로 대량 생성되고 사용자에게 실질적 가치가 없는 페이지"* 이고, **판정 기준은 생성 방식이 아니라 페이지당 가치**다.
>
> **그리고 도메인 단위로 작동한다.** 한 도메인이 판정을 받으면 이슈·토론 페이지까지 같이 죽는다. v0.9.0 의 성과 전체가 뉴스 하나에 걸린다.
>
> 발행 게이트 — 하나라도 못 지키면 **`/article/` 를 Disallow 로 두고 시작한다.** 색인은 나중에 켤 수 있지만 판정은 회복에 수개월이 걸린다.
>
> - 발행 전 **사람의 편집 검수**. 무검수 자동 발행 금지
> - 본문과 `NewsArticle` 에 **AI 생성 사실 명시**(`creditText` + 화면 상단 라벨)
> - `publisher` 는 조직(토론철). **가상의 기자 이름을 만들지 않는다**
> - **발행량을 인간 검수 역량에 연동**한다. 검수 없이 늘리지 않는다
> - 기사가 **토론철 1차 데이터**(찬반 수치·커뮤니티 분포·여론 변화)를 근거로 삼는다. 외부 기사 리라이트는 정확히 최대 피해 패턴이다
> - **인터넷신문 등록 여부 확인.** 등록 전에는 Disallow 유지가 안전하다
>
> **우리에게는 상쇄 카드가 있다.** 탐지 신호 중 "원본 조사 부재"를 정면으로 지우는 자산 — 찬반 수치·참여 커뮤니티 분포·발언 수·시간에 따른 여론 변화는 **다른 어디에도 없는 1차 데이터**다. 동시에 Cite Sources·Statistics 는 GEO 실측 상위 3위 기법이다. 두 목적이 같은 방향을 가리키는 드문 경우다.
>
> **발행 속도의 구체 수치는 규칙화하지 않는다.** "일 10건 이상이면 자동 생성 신호" 류의 주장이 돌지만 Google 공식 문서에 수치는 없다(블로그 단일 출처 ⚠). 다만 일 1,000건 계획이 나온다면 그 주장의 100배이고, **자릿수가 다르면 출처의 강도와 무관하게 논쟁의 여지가 없다.**
>
> 상세 절차·체크리스트·`generateSitemaps` 코드 패턴은 **`.claude/skills/seo-geo/references/ai-news.md`** 에 있다. 이건 v0.9.0 이 아니라 기사 기능 착수 시점의 결정 사항이다.

### 5.6 원문 단일 원칙 — 번역은 보기 계층이다

**한 엔티티 = 한 URL = 한 원문.** 토론철은 언어별 페이지를 만들지 않는다. 다른 언어 사용자를 위한 번역은 X(2026-04 Grok 자동 번역 전면 배포)처럼 **원문 위에 덧입히는 보기 기능**이다.

| 규칙 | 근거 |
|---|---|
| **SSR HTML 은 항상 원문**이다. 번역문을 서버 렌더하지 않는다 | Googlebot 은 **`Accept-Language` 없이**, 주로 **미국 IP** 로 크롤링한다(Google locale-adaptive pages). 같은 URL 에서 언어에 따라 본문을 바꾸면 한 버전만 색인되고, 기본값을 잘못 잡으면 **한국어 페이지가 색인에서 빠진다** |
| **사용자 신호 없이 자동으로 번역을 덧입히지 않는다.** 비로그인 사용자는 "번역 보기" 를 **직접 눌렀을 때**만 번역하고, 그 선택을 `localStorage` 에 기억한다 | Googlebot 은 JS 를 실행해 **렌더된 DOM 을 색인**한다. `navigator.language` 같은 브라우저 신호로 자동 번역하면 렌더러가 무엇을 보고할지 보장할 수 없다 ⚠(Google 미문서화) — 영어로 보고하면 번역본이 색인된다. 크롤러는 버튼을 누르지 않고 저장소도 유지하지 않으므로 명시적 선택은 안전하다. 익명 자동 번역은 봇 트래픽이 LLM 비용을 일으키는 문제도 있다 |
| **`Accept-Language`·IP 로 본문이나 경로를 바꾸지 않는다.** 자동 리다이렉트도 하지 않는다 | Google: "자동 리다이렉트를 피하라", "IP 분석으로 콘텐츠를 바꾸지 말라". **Next.js 16 공식 i18n 가이드의 `proxy` 리다이렉트 예시는 따르지 않는다** |
| 로그인 사용자는 **계정 언어 설정**으로 자동 번역하고, **클라이언트 아일랜드**에서 덧입힌다 | URL·SSR 과 독립. 크롤러는 로그인하지 않으므로 계정 설정의 영향을 받지 않는다. 크롤러가 보는 것 = 비로그인 첫 방문자가 보는 것이므로 클로킹이 아니다 |
| 번역문에는 **"○○어에서 번역됨" 라벨 + 원문 보기**를 항상 붙이고, 언어별로 끌 수 있게 한다 | 토론은 찬반 뉘앙스·반어가 뒤집히면 논쟁 자체가 왜곡된다. 원문이 언제나 권위다 |
| 번역은 **(콘텐츠 id, 대상 언어)** 단위로 캐시한다 | LLM 호출이 조회 수가 아니라 언어 수에 비례하게 된다 |
| hreflang·`alternates.languages`·로케일 접두어를 **쓰지 않는다** | 언어 버전 URL 이 없다. `<html lang="ko">` 를 유지한다 |

> **번역 기능 자체는 v0.9.0 범위가 아니다.** 이 절은 **나중에 번역을 넣더라도 SEO 를 깨지 않는 경계**를 미리 고정하는 것이다. 실행 방식·개인정보 문제는 §7-8.
>
> 레딧은 반대 길을 갔다 — 기계 번역 페이지를 `?tl=de` 별도 URL 로 만들고 hreflang 으로 묶어 **번역본을 검색에 노출**한다(2026-03~06 Reddit 인용의 5.7%, Google AI Overview 독일어 Reddit 인용의 52%). 그 길은 Google 이 권장하지 않는 파라미터 방식이고, 스팸 정책의 "번역 등 자동 변환" 리스크를 진다. 토론철은 택하지 않는다. 영어 검색 노출이 목표가 되면 §4.3f 의 조건으로 다시 연다.

### 6.2 `src/app/sitemap.ts`

단일 파일. 50개 URL 규모라 분할·페이지네이션·OOM 대책은 불필요하다(§3.3).

> **단, 사건·AI 기사가 생기면 자릿수가 바뀐다.** 기사만 일 1,000건 × 1년 = 36.5만 URL → 8개 샤드다. 그때 쓸 시그니처를 지금 고정해 둔다 — **Next.js 16 에서 `generateSitemaps` 의 `id` 가 Promise 로 전달된다.** 이전 버전의 평문 값 시그니처를 그대로 쓰면 깨진다.
>
> ```ts
> export default async function sitemap(props: { id: Promise<string> }) {
>   const id = Number(await props.id);  // ← Next.js 16: Promise<string>. 평문 값·number 로 받으면 깨진다
>   const start = id * 40_000;          // Google 한도 50,000 URL·50MB — 여유를 둔다
> }
> ```
>
> > 2026-10-19 정정 — 이전 판은 `Promise<number>` 로 적었다. 로컬 문서(`node_modules/next/dist/docs/.../sitemap.md` 버전 표: "v16.0.0 `id` is now a promise that resolves to a `string`")가 근거다.
>
> **v0.9.0 에는 넣지 않는다.** 50개 URL 에 샤딩은 순수 비용이다. `references/ai-news.md` §3.

| URL | 소스 | `lastModified` |
|---|---|---|
| `/`, `/map` | 정적 | 고정 상수 `STATIC_LAST_MODIFIED` |
| `/issue/{b36}` | `GET /api/v1/users/home` | `wiki.updatedAt` ?? 최신 스레드 활동 ?? `issue.createdAt` |
| `/debate/{b36}` | 이슈별 `GET /api/v2/room` | 스레드 최종 활동 시각 |

> **`ChatRoomResponse.updatedAt` 을 스레드 lastmod 로 쓰지 않는다** — v1.3.5 이관이 raw UPDATE 라 갱신되지 않아 대부분 생성일과 같다(백엔드 확인). 최종 채팅 시각은 §7-3 으로 따로 받는다.

> **제외 대상 (백엔드 PR #213, 미배포)** — HIDDEN 방은 목록·랭킹에서, ARCHIVED 이슈는 이슈맵·상세에서 빠지고 ARCHIVED 이슈 상세 `GET /api/v1/issue` 는 **404** 가 된다. sitemap 에서 둘 다 제외하고, 해당 상세 페이지도 404 로 응답한다(noindex↔sitemap 동기화 불변).

> **`lastModified` 에 `new Date()` 절대 금지.** 빌드할 때마다 전 URL 이 "방금 수정됨"으로 나가면 Google 이 lastmod 신호 자체를 신뢰하지 않게 되고, 회복에 수 주~수 개월이 걸린다.
>
> **문제 있음, 그리고 그대로 넘기지 않는다** — 현재 API 가 주는 시각 필드는 `issue.createdAt` 뿐이다. `IssueBriefResponse` 에 `updatedAt` 이 없고, `ThreadSummary` 에는 시각 필드가 아예 없다. 스레드의 최종 활동 시각을 알 수 없다. → §7-3 백엔드 요청. 그전까지는 `createdAt` 으로 정직하게 채운다(부정확한 최신 날짜보다 정확한 과거 날짜가 낫다).

> **AI 봇 3계층은 GEO 레버가 아니라 라이선스 결정이다.** (2026-08-21 리서치로 정정)
>
> 벤더별로 retrieval 봇과 training 봇이 따로 제어되는 것은 사실이다(`GPTBot`↔`OAI-SearchBot`, `ClaudeBot`↔`Claude-SearchBot`). **그러나 학습 봇을 막는다고 인용이 유지되지도, 열어둔다고 인용이 늘지도 않는다.**
>
> - `GPTBot` 을 차단해도 콘텐츠가 Common Crawl·Bing 인덱스를 통해 도달해 ChatGPT 가 인용한다
> - AI Mode 피인용 도메인의 **51.9%가 AI 크롤러를 차단 중**이다(전체 표본 15% 대비). 차단 도메인이 오히려 **3.5배 더 인용된다** — Google 의 그라운딩은 AI 전용 크롤러가 아니라 자기 인덱스를 읽기 때문
> - `Google-Extended`·`Applebot-Extended` 는 **HTTP 요청을 하지 않는 robots.txt 전용 opt-out 토큰**이다. 차단해도 검색 순위·Siri 노출에 영향이 없다
> - **`ChatGPT-User` 같은 user-triggered fetcher 는 robots.txt 를 지키지 않는다**(OpenAI·Google 모두 문서화). Anthropic 의 `Claude-User` 만 예외적으로 준수한다 → robots.txt 를 접근 통제로 착각하지 말 것
>
> **따라서 학습 봇 차단/허용은 저작권·사업 결정이다.** 토론철이 정식 인터넷신문사 등록을 목표로 한다면 법무 판단 사항이고(뉴스 발행사의 AI 크롤러 차단률은 56.4%로 일반 사이트의 5배다), SEO 로서는 어느 쪽도 권고하지 않는다. **결정된 정책을 robots.txt 에 정확히 옮기는 것까지가 우리 일이다.** → §7-9
>
> **`/relay/` 차단은 필수다.** PostHog 리버스 프록시 경로다(v0.8.0). 크롤러가 수집 엔드포인트를 두드리면 분석 데이터가 오염된다.
>
> **`kakaotalk-scrap` 허용은 우리에게 특히 중요하다.** 국내 유입의 상당수가 카카오톡 공유다. 막으면 링크 미리보기가 죽는다.

### 6.4 RSC 전환 — 실제 작업량의 대부분

패턴은 **서버 셸 + 클라이언트 아일랜드** 다.

```
page.tsx  (서버)  generateMetadata + JSON-LD + 위키 본문 + 스레드 목록 + 타임라인
  └─ <ChatIsland />  ("use client")  실시간 채팅·투표·소켓
```

- 크롤러는 서버 셸의 완성된 HTML 을 읽는다
- 사용자는 그 위에 하이드레이션된 인터랙션을 얻는다
- **핵심 콘텐츠가 클라이언트 아일랜드 안에 있으면 안 된다.** 그러면 다시 30자로 돌아간다
- 데이터 재검증: `apiFetch` 는 나머지 옵션을 `fetch` 로 그대로 넘기므로 `next: { revalidate: N }` 이 통한다. 위키·이슈는 길게(예: 1시간), 스레드 목록은 짧게

### 12.2 설계에서 바꾼 것

- **robots 는 단일 그룹이다.** §6.3 초안은 Googlebot·Bingbot 등을 따로 그룹으로 뒀는데, robots.txt 에서 이름을 가진 그룹이 있는 봇은 `*` 그룹을 **무시**한다. 그대로 두면 그 봇들에게 Disallow 가 사라진다. 한 그룹에 `User-Agent` 를 나열했다(Yeti·Daumoa 명시 유지)
- **AI 학습 봇은 막지 않았다.** 7-9 가 미결정이라 robots.txt 가 없던 때와 같은 "허용" 을 유지한다. 결정되면 별도 그룹으로 추가한다
- **`/*?*` Disallow 는 넣지 않았다.** 쿼리 URL 은 canonical 이 정리한다. 크롤을 막으면 canonical 자체를 못 읽는다
- **`/prod/` Disallow 추가** — 구버전 앱 REST 안전망 프록시
- **비노출 상태 404** — 이슈 `DRAFT`·`ARCHIVED`, 방 `HIDDEN`·`DELETED`·`CONTAINER`. sitemap 도 같은 규칙(`DORMANT` 는 노출 유지)
