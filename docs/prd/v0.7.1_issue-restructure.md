### 2.1 이미 배포됨 — 2026-07-23 01:13 KST

| 변경 | 웹 영향 |
|---|---|
| `POST /api/v1/issue` → **ADMIN 전용** | **없음** (호출처 0건) |
| `POST /api/v1/room` → **ADMIN 전용** | **없음** (호출처 0건) |
| 신규 에러코드 `ACCESS_DENIED` (403) | **없음** — `apiFetch` 가 `body.code`/`body.message` 를 그대로 사용 (`src/lib/api/client.ts:80-85`) |

권한 실패 응답 형식(기존과 동일한 envelope):
- 비로그인 → `401` / `MISSING_ACCESS_TOKEN` / "Access Token이 필요합니다."

> `MISSING_ACCESS_TOKEN` 은 토큰 자체가 없는 경우라 `client.ts:71` 의 refresh 재시도 분기(`res.status === 401 && token`)를 타지 않고 바로 에러로 떨어진다. 의도된 동작.

**운영 API 베이스**: `https://api.toronchul.app/prod` — `/prod` 접두사 필수. 빠지면 톰캣이 HTML 404 를 반환해 원인 추적이 어렵다.

### 2.3 호환성 약속 (백엔드 → 웹/앱)

앱은 스토어 심사로 웹보다 며칠 늦게 반영된다. 그 기간 백엔드가 구버전 앱을 동시 지원한다.

- **응답 필드를 제거·개명·의미 변경하지 않는다.** 추가만 한다.
- **요청의 새 필드는 항상 optional.**
- 그래도 바꿔야 하면 `/api/v2/...` 로 신규 엔드포인트를 파고 기존 것을 유지한다.

**웹에 대한 함의: 새 구조를 먼저 개발해도 되고, 그동안 기존 API 는 계속 동작한다.** 초판 §8 이 요청했던 `ChatRoomResponse.agree/disagree/opinion` **제거 요청은 철회한다** — 백엔드는 이 필드를 **대표 주제 기준으로 계속 채운다**(§4.3). 웹은 읽지 않으면 된다.

> 실측으로 확인됨(§2.4-C-3): 옛 방 id 로의 직접 조회가 컨테이너+필터 조회와 **완전히 동일한 결과**를 낸다. 약속이 실제로 지켜지고 있다.

### 2.4 2026-07-29 운영 API 실측

**방법**: `https://api.toronchul.app/prod/v3/api-docs` 스웨거 전량 + 로그인 세션 토큰으로 실제 응답 확인. 불문율 #1(추측 금지)을 만족한다.

#### A. 배포되어 있는 것

| 엔드포인트 | 내용 |
|---|---|
| `GET /api/v2/room?issue-id=` | 컨테이너 방 + 스레드 목록. **`src/lib/api/room.ts` 에 반영 완료** |
| `GET /api/v2/wiki?issue-id=` | **이슈당 위키 1장**(게시본). 미게시면 전 필드 null, 에러 아님 |
| `POST /api/v1/admin/wiki/generate?issue-id=` | **AI 초안 생성** — LLM 이 DRAFT 리비전 저장(게시 안 함). 생성기 미구성 시 503 `WIKI_GENERATION_UNAVAILABLE` |
| `POST /api/v1/admin/wiki/revisions` | ADMIN 수동 리비전 추가 `{issueId, content(Markdown), editSummary}` |
| `POST /api/v1/admin/wiki/publish` | `{revisionId}` → PUBLISHED 전환. 옛 리비전 id 로 재게시 = **롤백** |
| `GET /api/v1/chat/rooms/{roomId}/messages?threadId=` | **스레드 필터** — 스웨거 설명에 "웹 탭"이라 명시 |

#### B. 배포되지 않은 것

- **토론 주제(topic) 계열 엔드포인트 0개.** 생성·수정·삭제·주제단위 투표 전부 없다.
- **주제 종료(CLOSED) 개념이 API 에 노출되지 않는다.** `ThreadSummary` 에 status 필드가 없다.
- → `TopicCreateSheet`, `LiveTopicStrip`, 종료/읽기전용 UI 는 **지금 만들 수 없다**(§12-2).

#### C. 데이터 실측

1. **컨테이너 마이그레이션 완료** — 이슈 11건(6~20) 전부 컨테이너 방 보유(`containerRoomId` 153~163). null 인 이슈 0건. 기존 방 57~83 이 그대로 스레드가 됐다.
2. **스레드 분할 정확** — 컨테이너 153 전체 196건 = thread 57(113) + thread 58(83). 미분류(`threadId: null`) 메시지 **0건**.
3. **구버전 앱 호환 확인** — `GET /rooms/58/messages` 와 `GET /rooms/153/messages?threadId=58` 이 **동일 결과**(83건, 동일 페이지).
4. **없는/타 이슈 threadId → 에러 아님** — `threadId=99999`, 타 이슈 `threadId=76` 모두 `200` + `totalCount: 0`. 404 처리 불필요.
5. **커서는 메시지 id** (`"430"`, `"327"`). 전체 스트림 커서를 스레드 필터에 재사용하면 **이미 본 메시지가 다시 내려온다.** §4.2 의 경고가 실측으로 확인됨 → 모드별 커서 분리 **필수**.
6. **투표는 스레드에만 존재** — `GET /api/v1/room?chatroom-id=153`(컨테이너) → `agree:0 / disagree:0 / opinion:NEUTRAL`. `chatroom-id=58`(스레드) → `45 / 26`. **컨테이너 방은 투표 대상이 아니다.**
7. **위키 전 이슈 미게시** — 11개 이슈 모두 `status/content/revisionId/updatedAt` null. AI 초안이 아직 한 건도 생성·게시되지 않았다.

#### D. 실측 못 한 것

**`opinionType` 서버 판정 여부(§4.4, §9-5)** — 읽기로는 판별 불가. 기존 메시지가 전부 배지를 갖고 있는데, 옛 UI 가 투표를 해야 입장시켰으므로 "서버 판정"과 "클라이언트 값 저장"이 같은 결과로 보인다. 테스트 계정도 전 스레드에 이미 투표되어 있어 미투표 경로를 쓸 수 없다. → **운영 채팅방에 메시지 1건을 써야 판별된다**(§12-1).

## 3. 도메인 모델

```
이슈 (Issue)                        ← 최상위. ADMIN 생성.
├── 토론위키 (DebateWiki)            ← ★ 이슈당 1장. 토론철 AI 작성 + ADMIN 게시.
└── 컨테이너 채팅방 (ChatRoom)        ← 이슈당 1개. ADMIN 생성. 상시 개방, 투표 불필요.
     ├── 일반 발언                   threadId = NULL
     └── 스레드 (= 기존 채팅방) [*]   ← ★ 찬반이 여기 붙는다. 현재는 ADMIN 생성.
          ├── 스레드 발언             threadId = N
          └── 찬반 (스레드 단위 투표)
```

> **2026-07-29 개정**: 초판·2026-07-23 판은 `채팅방 → 토론 주제(유저 생성) → 위키(주제 1:1)` 3단이었다. 실제 배포는 **`이슈 → 컨테이너 방 → 스레드`** 이고 **위키는 이슈 1:1** 이다. 주제(topic) 층은 미배포이므로 현재 "스레드 = 기존 채팅방"으로 읽는다.

### 3.1 각 개념

**컨테이너 채팅방** — 이슈에 1:1 로 붙는 새 방(153~163). 모바일이 구독·입장하는 대상이며 STOMP 도 이 id 기준이다. 메시지는 전부 이 방에 모이고 `threadId` 로 소속이 갈린다.

**스레드** — 기존 채팅방(57~83)이 그대로 스레드가 된 것. **찬반 투표가 붙는 유일한 층위.** 아직 유저가 만들 수 없다.

**토론위키 (DebateWiki)** — **이슈와 1:1.** 토론철 AI 가 이슈의 원천 재료로 초안을 쓰고 ADMIN 이 게시한다. **유저 편집 없음**(§6.3). 웹은 **읽기 전용 렌더**만 담당한다.

### 3.2 상태 전이

```
[이슈 생성]
     │  ADMIN: POST /admin/wiki/generate  (AI 초안 → DRAFT 리비전)
     ▼
 DebateWiki(미게시)  ── status/content = null, 웹은 "준비 중" 안내
     │  ADMIN: POST /admin/wiki/publish {revisionId}
     ▼
 DebateWiki(PUBLISHED)  ── content(Markdown) 렌더
     │  옛 revisionId 로 재게시 = 롤백
     ▼
 (반복)
```

- 웹이 구분할 상태는 **미게시 / 게시됨** 둘뿐이다. `ACTIVE/ARCHIVED/HIDDEN` 3상태 설계는 폐기.
- 스레드의 `OPEN/CLOSED` 는 API 에 아직 없다(§2.4-B).

### 3.3 찬반 투표의 이동

| | v0.7 (현행) | v0.7.1 |
|---|---|---|
| 투표 대상 | 채팅방 | **스레드** (= 옛 방 id) |
| 투표 시점 | 입장 **전** (강제) | 열람 중 아무 때나 (선택) |
| 미투표 시 | 채팅 입장 불가 | **채팅 자유 참여** |
| 미투표 표현 | — | `myOpinion: "NEUTRAL"` (비로그인 포함) |
| API | `POST /room/vote` | **`POST /room/vote` 그대로** — 스레드 id 를 넘기면 된다(§2.4-C-6) |

> 주제 단위 투표 API 는 미배포다. 스레드 = 옛 방이므로 기존 `voteRoom()` 이 그대로 정답이다.

## 4. 백엔드 데이터 구조

> ⚠️ **불문율 #1**: 아래 §4.1 은 백엔드 v1.3.4 PRD 의 **설계 문서**이고, 실제 배포 상태는 **§2.4 실측**이 정본이다. 충돌 시 §2.4 를 따른다.

### 4.1 신규 테이블 (참고용 — 응답 필드명은 별개)

```
debate_topic          topic_id, chat_room_id, issue_id(비정규화), title,
                      status(OPEN/CLOSED), opened_at, closed_at,
                      agree_count, disagree_count, created_by     ← API 미노출
user_topic_opinion    user_id, topic_id, opinion(AGREE/DISAGREE)  ← API 미노출
debate_wiki           wiki_id, issue_id(1:1), status, current_revision_id
                      ★ 설계상 topic_id 1:1 이었으나 실제는 issue_id 1:1
debate_wiki_revision  revision_id, wiki_id, content, source(AI/ADMIN), model,
                      edited_by, edit_summary
chat                  + thread_id (nullable)
chat_room             + default_topic_id  ← 대표 주제 shim
```

### 4.2 스레드 조회 두 모드

| 모드 | 용도 | 웹 |
|---|---|---|
| 전체 스트림 | 컨테이너 방 기본 화면. 스레드 발언도 인라인으로 함께 보이고 소속 배지를 단다 | **기존 조회 경로 그대로** — 무회귀 |
| 스레드 필터 | 특정 스레드만 골라 보기 (`?threadId=`) | 신규 |

- **커서는 모드별로 독립**이다. **2026-07-29 실측으로 확인**(§2.4-C-5): 커서는 메시지 id 이고, 전체 스트림 커서를 스레드 뷰에 재사용하면 이미 본 메시지가 재노출된다. 웹은 커서 상태를 **모드별로 분리 보관**한다.
- 없는 threadId 는 200 + 빈 배열이므로 **에러 분기 불필요**(§2.4-C-4).

### 4.3 대표 주제(default topic) shim — 구버전 앱 호환

마이그레이션에서 채팅방마다 "첫 주제"를 만들어 **대표 주제**로 지정한다(`chat_room.default_topic_id`).

- 구 API `POST /api/v1/room/vote` → 그 방의 **대표 주제에 투표**하는 것으로 라우팅
- 구 API `GET /api/v1/room` 의 `agree`/`disagree`/`opinion` → **대표 주제 기준**으로 계속 채워짐

**웹에 대한 함의**: `src/lib/api/room.ts` 의 `voteRoom()` 은 **그대로 동작한다.** 실측(§2.4-C-6)에서 스레드 id 로 조회 시 정상적인 집계(`45/26`)가 나오고, 컨테이너 id 로는 `0/0` 이 나온다 → **투표 API 에는 반드시 스레드 id 를 넘긴다.**

> ~~확인 필요(§9-4): 대표 주제가 CLOSED 되면 구 앱 투표가 어디로 가는가.~~ → **주제 종료 개념이 API 에 없으므로(§2.4-B) 당분간 실효 없는 질문.** 종료 기능 배포 시 재확인.

### 4.4 `opinionType` — 서버 판정 + 발언 시점 고정

현재 웹은 메시지 전송 시 `opinionType` 을 **클라이언트 값으로 실어 보낸다**(`src/components/room/ChatRoom.tsx:235`, `src/lib/api/chatSocket.ts:168`). 백엔드는 이를 **서버 판정**으로 바꾼다.

```
메시지의 threadId == NULL          → 배지 없음
메시지의 threadId == N
   ├ 해당 스레드에 투표 있음         → 그 값 (AGREE / DISAGREE)
   └ 없음                         → 배지 없음
```

- **발언 시점에 고정(snapshot)한다.** 나중에 입장을 바꿔도 과거 발언의 배지는 그대로다.
- **전환 완료 여부 미확인** — §2.4-D. 판별하려면 실제 투표와 **반대되는** `opinionType` 을 실어 메시지 1건을 보내고 배지를 되받아야 한다(§12-1).
- **웹 작업**: 판별 후 `opinionType` 전송 제거. `src/lib/api/chatSocket.ts:161` 의 "클라이언트 값을 사용한다" 주석도 함께 정리.

## 6. 설계 결정 3건 — **2026-07-29 전부 확정**

### 6.1 위키 편집 단위 — **확정: 문서 전체 리비전** ✅

`POST /api/v1/admin/wiki/revisions` 의 바디가 `{issueId, content(Markdown), editSummary}` 로 배포됐다. 문단 단위가 아니다. **리비전 저장과 게시가 분리**되어 있고, 옛 리비전 id 로 재게시하면 롤백이다.

→ `WikiBlockEditor.tsx` 범위 제외 유지. 웹은 편집을 하지 않으므로 **`content` 를 Markdown 으로 렌더하기만 하면 된다.**

### 6.2 AI 초안 — **확정: 있다** ✅ (잠정 전제와 반대)

`POST /api/v1/admin/wiki/generate` 가 배포되어 있다 — "이슈의 원천 재료로 LLM 초안을 생성해 DRAFT 리비전으로 저장(게시 안 함)". 전용 에러코드 `WIKI_GENERATION_UNAVAILABLE`(503), 응답에 `model` 필드.

→ 잠정 전제("AI 초안 없이 가고 웹이 빈 상태를 UX 로 처리")는 **폐기**. "첫 문단을 작성해보세요" CTA·작성 템플릿은 만들지 않는다. 웹이 처리할 빈 상태는 **"AI 초안이 아직 게시되지 않음"** 하나다.

### 6.3 위키 편집 권한 — **확정: 토론철 AI + ADMIN 전용** ✅

쓰기 엔드포인트 3개가 전부 `/api/v1/admin/wiki/*` 하위다. 일반 유저용 위키 쓰기 API 는 존재하지 않는다. **2026-07-29 기획 확정: 위키는 토론철 AI 가 쓴다.**

→ 잠정 전제("ADMIN + 주제 작성자")보다 좁게 확정. `WikiDocument` 의 편집 버튼·`WikiRevisionList` 는 **범위에서 제외**.

> 이전 판의 "사실상 작성자의 글이 된다" 우려는 **해소**됐다. 집단 편집 위키가 아니라 **AI 가 정리하는 이슈 브리핑 문서**로 성격이 확정됐기 때문이다. 되돌리기·편집 잠금·훼손 대응은 불필요.

2. `IssueThreadTabs` 가 v2 에서 받은 `agreeCount/disagreeCount/myOpinion` 을 쓰지 않고 `RoomDetail` 이 스레드마다 v1 상세를 다시 호출한다 → 탭 전환마다 왕복 1회.
