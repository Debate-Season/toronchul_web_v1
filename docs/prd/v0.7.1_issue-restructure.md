### 2.3 호환성 약속 (백엔드 → 웹/앱)

앱은 스토어 심사로 웹보다 며칠 늦게 반영된다. 그 기간 백엔드가 구버전 앱을 동시 지원한다.

- **응답 필드를 제거·개명·의미 변경하지 않는다.** 추가만 한다.
- **요청의 새 필드는 항상 optional.**
- 그래도 바꿔야 하면 `/api/v2/...` 로 신규 엔드포인트를 파고 기존 것을 유지한다.

**웹에 대한 함의: 새 구조를 먼저 개발해도 되고, 그동안 기존 API 는 계속 동작한다.** 초판 §8 이 요청했던 `ChatRoomResponse.agree/disagree/opinion` **제거 요청은 철회한다** — 백엔드는 이 필드를 **대표 주제 기준으로 계속 채운다**(§4.3). 웹은 읽지 않으면 된다.

> 실측으로 확인됨(§2.4-C-3): 옛 방 id 로의 직접 조회가 컨테이너+필터 조회와 **완전히 동일한 결과**를 낸다. 약속이 실제로 지켜지고 있다.

### 2.4 2026-07-29 운영 API 실측

**방법**: `https://api.toronchul.app/prod/v3/api-docs` 스웨거 전량 + 로그인 세션 토큰으로 실제 응답 확인. 불문율 #1(추측 금지)을 만족한다.

#### A. 배포되어 있는 것

| 엔드포인트 | 내용 |
|---|---|
| `GET /api/v2/room?issue-id=` | 컨테이너 방 + 스레드 목록. **`src/lib/api/room.ts` 에 반영 완료** |
| `GET /api/v1/chat/rooms/{roomId}/messages?threadId=` | **스레드 필터** — 스웨거 설명에 "웹 탭"이라 명시 |
| 위키 4종 (`GET /api/v2/wiki`, `admin/wiki/generate·revisions·publish`) | 배포돼 있으나 **웹 구현은 v1.1.0 §1.2 로 이관.** 게시본 0건 |

#### B. 배포되지 않은 것

- **토론 주제(topic) 계열 엔드포인트 0개.** 생성·수정·삭제·주제단위 투표 전부 없다.
- **주제 종료(CLOSED) 개념이 API 에 노출되지 않는다.** `ThreadSummary` 에 status 필드가 없다.
- → `TopicCreateSheet`, `LiveTopicStrip`, 종료/읽기전용 UI 는 **지금 만들 수 없다**(§12-2).

#### C. 데이터 실측

1. **컨테이너 마이그레이션 완료** — 이슈 11건(6~20) 전부 컨테이너 방 보유(`containerRoomId` 153~163). null 인 이슈 0건. 기존 방 57~83 이 그대로 스레드가 됐다.
2. **스레드 분할 정확** — 컨테이너 153 전체 196건 = thread 57(113) + thread 58(83). 미분류(`threadId: null`) 메시지 **0건**.
3. **구버전 앱 호환 확인** — `GET /rooms/58/messages` 와 `GET /rooms/153/messages?threadId=58` 이 **동일 결과**(83건, 동일 페이지).
4. **없는/타 이슈 threadId → 에러 아님** — `threadId=99999`, 타 이슈 `threadId=76` 모두 `200` + `totalCount: 0`. 404 처리 불필요.
5. **커서는 메시지 id** (`"430"`, `"327"`). 전체 스트림 커서를 스레드 필터에 재사용하면 **이미 본 메시지가 다시 내려온다.** §4.2 의 경고가 실측으로 확인됨 → 모드별 커서 분리 **필수**.
6. **투표는 스레드에만 존재** — `GET /api/v1/room?chatroom-id=153`(컨테이너) → `agree:0 / disagree:0 / opinion:NEUTRAL`. `chatroom-id=58`(스레드) → `45 / 26`. **컨테이너 방은 투표 대상이 아니다.**
7. **위키 전 이슈 미게시** — 11개 이슈 모두 `status/content/revisionId/updatedAt` null. AI 초안이 아직 한 건도 생성·게시되지 않았다. → **이 실측이 위키를 v1.1.0 으로 미룬 직접적 근거다.**

#### D. 실측 못 한 것

**`opinionType` 서버 판정 여부(§4.4, §9-5)** — 읽기로는 판별 불가. 기존 메시지가 전부 배지를 갖고 있는데, 옛 UI 가 투표를 해야 입장시켰으므로 "서버 판정"과 "클라이언트 값 저장"이 같은 결과로 보인다. 테스트 계정도 전 스레드에 이미 투표되어 있어 미투표 경로를 쓸 수 없다. → **운영 채팅방에 메시지 1건을 써야 판별된다**(§12-1).

## 3. 도메인 모델

```
이슈 (Issue)                        ← 최상위. ADMIN 생성.
├── 토론위키 (DebateWiki)            ← 이슈당 1장. AI 작성. **웹 구현은 v1.1.0 §1**
└── 컨테이너 채팅방 (ChatRoom)        ← 이슈당 1개. ADMIN 생성. 상시 개방, 투표 불필요.
     ├── 일반 발언                   threadId = NULL
     └── 스레드 (= 기존 채팅방) [*]   ← ★ 찬반이 여기 붙는다. 현재는 ADMIN 생성.
          ├── 스레드 발언             threadId = N
          └── 찬반 (스레드 단위 투표)
```

> **2026-07-29 개정**: 초판·2026-07-23 판은 `채팅방 → 토론 주제(유저 생성) → 위키(주제 1:1)` 3단이었다. 실제 배포는 **`이슈 → 컨테이너 방 → 스레드`** 이고 **위키는 이슈 1:1** 이다. 주제(topic) 층은 미배포이므로 현재 "스레드 = 기존 채팅방"으로 읽는다.

### 3.1 각 개념

**컨테이너 채팅방** — 이슈에 1:1 로 붙는 새 방(153~163). 모바일이 구독·입장하는 대상이며 STOMP 도 이 id 기준이다. 메시지는 전부 이 방에 모이고 `threadId` 로 소속이 갈린다.

**스레드** — 기존 채팅방(57~83)이 그대로 스레드가 된 것. **찬반 투표가 붙는 유일한 층위.** 아직 유저가 만들 수 없다.

**토론위키 (DebateWiki)** — **이슈와 1:1.** 토론철 AI 가 초안을 쓰고 ADMIN 이 게시한다. 유저 편집 없음. 데이터 모델만 여기 남기고 **화면·API·상태 전이는 v1.1.0 §1 로 이관**했다.

### 3.2 상태 전이

- **위키**의 상태 전이(미게시 → PUBLISHED → 롤백)는 **v1.1.0 §1.3** 으로 이관.
- **스레드**의 `OPEN/CLOSED` 는 API 에 아직 없다(§2.4-B). 웹이 구분할 스레드 상태는 현재 없다.

### 3.3 찬반 투표의 이동

| | v0.7 (현행) | v0.7.1 |
|---|---|---|
| 투표 대상 | 채팅방 | **스레드** (= 옛 방 id) |
| 투표 시점 | 입장 **전** (강제) | 열람 중 아무 때나 (선택) |
| 미투표 시 | 채팅 입장 불가 | **채팅 자유 참여** |
| 미투표 표현 | — | `myOpinion: "NEUTRAL"` (비로그인 포함) |
| API | `POST /room/vote` | **`POST /room/vote` 그대로** — 스레드 id 를 넘기면 된다(§2.4-C-6) |

> 주제 단위 투표 API 는 미배포다. 스레드 = 옛 방이므로 기존 `voteRoom()` 이 그대로 정답이다.

## 4. 백엔드 데이터 구조

> ⚠️ **불문율 #1**: 아래 §4.1 은 백엔드 v1.3.4 PRD 의 **설계 문서**이고, 실제 배포 상태는 **§2.4 실측**이 정본이다. 충돌 시 §2.4 를 따른다.

### 4.1 신규 테이블 (참고용 — 응답 필드명은 별개)

```
debate_topic          topic_id, chat_room_id, issue_id(비정규화), title,
                      status(OPEN/CLOSED), opened_at, closed_at,
                      agree_count, disagree_count, created_by     ← API 미노출
user_topic_opinion    user_id, topic_id, opinion(AGREE/DISAGREE)  ← API 미노출
debate_wiki           wiki_id, issue_id(1:1), status, current_revision_id   ← v1.1.0
debate_wiki_revision  revision_id, wiki_id, content, source(AI/ADMIN), model,
                      edited_by, edit_summary                              ← v1.1.0
chat                  + thread_id (nullable)
chat_room             + default_topic_id  ← 대표 주제 shim
```

### 4.2 스레드 조회 두 모드

| 모드 | 용도 | 웹 |
|---|---|---|
| 전체 스트림 | 컨테이너 방 기본 화면. 스레드 발언도 인라인으로 함께 보이고 소속 배지를 단다 | **기존 조회 경로 그대로** — 무회귀 |
| 스레드 필터 | 특정 스레드만 골라 보기 (`?threadId=`) | 신규 |

- **커서는 모드별로 독립**이다. **2026-07-29 실측으로 확인**(§2.4-C-5): 커서는 메시지 id 이고, 전체 스트림 커서를 스레드 뷰에 재사용하면 이미 본 메시지가 재노출된다. 웹은 커서 상태를 **모드별로 분리 보관**한다.
- 없는 threadId 는 200 + 빈 배열이므로 **에러 분기 불필요**(§2.4-C-4).

### 4.3 대표 주제(default topic) shim — 구버전 앱 호환

마이그레이션에서 채팅방마다 "첫 주제"를 만들어 **대표 주제**로 지정한다(`chat_room.default_topic_id`).

- 구 API `POST /api/v1/room/vote` → 그 방의 **대표 주제에 투표**하는 것으로 라우팅
- 구 API `GET /api/v1/room` 의 `agree`/`disagree`/`opinion` → **대표 주제 기준**으로 계속 채워짐

**웹에 대한 함의**: `src/lib/api/room.ts` 의 `voteRoom()` 은 **그대로 동작한다.** 실측(§2.4-C-6)에서 스레드 id 로 조회 시 정상적인 집계(`45/26`)가 나오고, 컨테이너 id 로는 `0/0` 이 나온다 → **투표 API 에는 반드시 스레드 id 를 넘긴다.**

> ~~확인 필요(§9-4): 대표 주제가 CLOSED 되면 구 앱 투표가 어디로 가는가.~~ → **주제 종료 개념이 API 에 없으므로(§2.4-B) 당분간 실효 없는 질문.** 종료 기능 배포 시 재확인.

### 4.4 `opinionType` — 서버 판정 + 발언 시점 고정

현재 웹은 메시지 전송 시 `opinionType` 을 **클라이언트 값으로 실어 보낸다**(`src/components/room/ChatRoom.tsx:235`, `src/lib/api/chatSocket.ts:168`). 백엔드는 이를 **서버 판정**으로 바꾼다.

```
메시지의 threadId == NULL          → 배지 없음
메시지의 threadId == N
   ├ 해당 스레드에 투표 있음         → 그 값 (AGREE / DISAGREE)
   └ 없음                         → 배지 없음
```

- **발언 시점에 고정(snapshot)한다.** 나중에 입장을 바꿔도 과거 발언의 배지는 그대로다.
- **전환 완료 여부 미확인** — §2.4-D. 판별하려면 실제 투표와 **반대되는** `opinionType` 을 실어 메시지 1건을 보내고 배지를 되받아야 한다(§12-1).
- **웹 작업**: 판별 후 `opinionType` 전송 제거. `src/lib/api/chatSocket.ts:161` 의 "클라이언트 값을 사용한다" 주석도 함께 정리.

### 5.2 이슈 상세

```
┌ 헤더: 이슈명 · 토론 주제 N개
├ 참여 커뮤니티 (아이콘)

│  ┌ 사전투표 절차는 신뢰할 만한가?  ┐
│  │ 52% ▓▓▓▓▓░░░░░ 48%           │  ← 누르면 이 주제 탭이 열린 토론방
│  └──────────────────────────────┘
│  ┌ 정당·도덕성이 더 중요한가?      ┐
└  └──────────────────────────────┘
```

- 찬반 수치는 `GET /api/v2/room` 이 스레드마다 내려주므로 **방별 추가 조회를 하지 않는다**(v0.7 은 카드마다 1회 왕복했다).
- 사건 탭 · 미디어 탭 · 위키 탭은 **v1.1.0**.

### 5.3 토론방 (= 채팅)

```
┌ ← 제21대 대통령 선거          ← 이슈로 돌아가기 (고정)
├ 주제 탭 ──────────────────── (가로 스크롤, 고정)
│  ( 사전투표 절차 )( 정당·도덕성 )( TV토론 )
├ ─────────────────────────────────
│  (메시지 목록 — 여기만 세로 스크롤)
├ ─────────────────────────────────
└ [입력창]  — 로그인만 필요. 투표 불필요. (고정)

    주제 · 찬반 게이지 · 투표 버튼은 → 우측 사이드바 (§6.3)
    (모바일은 사이드바가 없어 탭 아래 본문에 렌더)
```

- **투표 게이팅 없음.** 투표는 내 말풍선의 정렬·색(`opinionType`)만 바꾼다. 투표하지 않은 사용자는 `NEUTRAL` 로 발언한다.
- **스크롤 축이 둘뿐이다** — 주제 탭의 가로, 메시지 목록의 세로. 나머지는 전부 고정 (§6.1).
- 본문에는 **공지 블록을 만들지 않는다** (§6.2).
- **탭 전환 = 스레드 방 재구독.** 커서·메시지 목록이 통째로 갈리므로 `key={threadId}` 로 `ChatRoom` 을 다시 마운트한다 — 커서 혼입(§4.2)이 구조적으로 불가능하다.
- 비로그인은 탭·찬반 현황까지만 보인다. 메시지 조회가 401 이라 대화 영역만 로그인 안내로 대체한다.
- 우측 사이드바는 **이 이슈의 토론 주제 목록**으로 교체한다 (§6.3).
- "전체" 탭은 **없다.** 컨테이너 방 구독이 전제인데 지금은 스레드 방을 쓴다(§5.5).
- "토론 주제 만들기" CTA 는 **주제 생성 API 배포 후**(§12-2).

### 5.5 STOMP 대상 — 스레드 방 유지 (2026-08-15 백엔드 확인)

컨테이너 방 구독이 최종 형태지만 **지금 옮기면 앱과 실시간이 갈라진다.** 백엔드 코드 확인 결과:

- `WebSocketControllerV1` 의 `@SendTo("/topic/room{roomId}")` 가 전부다. **fan-out 이 없다** — 발행한 주소로만 브로드캐스트된다.
- 운영 중인 앱은 스레드 방(71/72/73)에 구독 중이다. 웹만 컨테이너(157)로 옮기면 저장은 합쳐지지만 **실시간만 서로 안 보인다**(새로고침하면 보이는 최악의 형태).

→ 웹도 스레드 방을 쓴다: 조회 `fetchMessages(71)` · 구독 `/topic/room71` · 발행 `/stomp/chat.room.71`.

| | `roomId` | `threadId` |
|---|---|---|
| REST `fetchMessages(71)` | **157** (컨테이너) | 71 |
| 소켓 `/topic/room71` | **71** (발행 주소) | 71 |

- ⚠️ `roomId` 는 REST 와 소켓이 다른 값이다. 탭 판별이 필요해지면 **`threadId` 기준으로만** 한다.

## 6. 화면 개선 4건 — 2026-08-17 추가

> 위키 설계 결정 3건(편집 단위 · AI 초안 · 편집 권한)이 있던 자리다. 전부 확정된 상태로 **v1.1.0 §1.5** 로 옮겼다. 이 자리는 IA 축소 이후 드러난 **토론방·전역 내비 화면 문제 4건**이 대신 채운다.

### 6.1 토론방 — 가로/세로 스크롤 축 분리

**문제**: IA 를 2단으로 줄이면서 토론방 한 화면에 얹히는 것이 늘었다(이슈 링크 · 주제 탭 · 주제 · 찬반 · 대화 · 입력창). 그대로 두면 페이지 전체가 세로로 밀려서 **입력창이 화면 밖으로 나가고, 채팅을 치려면 스크롤을 내려야 하는** 형태가 된다.

**결정**: 토론방은 **스크롤 축을 둘로 못 박는다.**

| 축 | 대상 | 나머지 |
|---|---|---|
| **가로** | 주제 탭 (`ThreadTabs`) | 탭 줄바꿈 없음. 넘치면 가로로만 흐른다 |
| **세로** | 메시지 목록 (`ChatRoom` 내부) | 페이지 본문은 세로로 **스크롤하지 않는다** |

- 높이는 `DebateRoom` 이 한 번만 계산한다(`100dvh` − 레이아웃 패딩). `ChatRoom` 은 `min-h-0 flex-1` 로 남는 높이를 채운다.
- 이슈 링크 · 주제 탭 · 공지 · 입력창은 전부 `flex-shrink-0` 고정. 화면이 좁아져도 사라지는 것은 **메시지 목록의 보이는 범위**뿐이다.
- 주제가 많아도 탭이 2줄이 되지 않으므로 **대화 영역 높이가 주제 개수에 흔들리지 않는다.** 선택된 탭은 진입 시 `scrollIntoView({ block: "nearest", inline: "nearest" })` 로 가로 스크롤만 맞춘다 — 페이지 세로 위치는 건드리지 않는다.
- `dvh` 를 쓰는 이유는 모바일 주소창 높이 변화 때문이다. `vh` 면 주소창이 접힐 때 입력창이 잘린다.

### 6.2 본문에서 주제·찬반을 걷어낸다 — 공지 블록은 만들지 않는다

**문제**: 주제 제목(`<h1>`)과 찬반 게이지·버튼(`ThreadVoteBar`)이 **탭 바로 아래 떠 있는 별개 요소**였다. 경계가 없어서 탭의 일부인지 대화의 일부인지 읽히지 않고, 무엇보다 **대화 높이를 그만큼 먹는다.**

**결정**: 셋을 본문에서 빼서 **우측 사이드바로 옮긴다**(§6.3). 본문은 이슈 링크 → 주제 탭 → 대화만 남는다.

```
├ ← 제21대 대통령 선거
├ 주제 탭 ──────────────────────── (가로 스크롤)
├ ────────────────────────────────
│ (메시지 목록 — 여기만 세로 스크롤)
└ [입력창]
```

- **"채팅 공지" 블록은 만들지 않는다.** 주제·찬반은 공지가 아니고, 지금 표시할 공지 내용도 없다. 빈 슬롯이나 자리표시자를 두지 않는다.
- 공지 기능이 실제로 생기면 그때 블록을 만든다. 후보: 운영 공지, 주제 종료 안내(주제 층 배포 후), 접속자 수(v1.1.0 §4.1).

> **개정 이력**: 2026-08-17 초안은 이 자리에 `RoomNotice`(주제+찬반을 감싼 공지 카드)를 두는 설계였다. 같은 날 **주제·찬반은 공지가 아니라 사이드바**로 확정되어 폐기했다.

### 6.3 우측 사이드바 — 현재 주제 · 찬반 게이지 · 투표 버튼

**문제**: 우측 사이드바(`RightSidebar`)가 어느 화면에서나 **"실시간 핫한 토론"** 고정이다. 토론방 안에서 남의 인기 토론은 쓸모가 적고, 정작 **지금 보고 있는 주제와 찬반**은 본문에서 대화 높이를 깎아먹고 있었다.

**결정**: **토론방 라우트에서만** 우측 사이드바를 **현재 스레드의 주제 패널**로 바꾼다.

| 라우트 | 우측 사이드바 |
|---|---|
| `/`, `/map`, `/issue/[id]/[slug]` 등 | 실시간 핫한 토론 (현행 유지) |
| `/issue/[id]/[slug]/[threadId]/[threadSlug]` | **현재 주제 + 찬반 게이지 + 찬반 투표 버튼** |

```
┌ 우측 사이드바 ──────────────────┐
│ 💬 사전투표 절차는 신뢰할 만한가? │  ← 현재 스레드의 주제
│    52% ▓▓▓▓▓░░░░░ 48%          │  ← 찬반 게이지
│    [👍 찬성]      [👎 반대]      │  ← 투표 버튼
└────────────────────────────────┘
```

- **주제 "목록"이 아니라 현재 주제 하나다.** 주제 간 이동은 상단 가로 탭이 이미 한다 — 목록을 사이드바에도 두면 같은 것이 두 번 나온다.
- 투표는 여전히 **입장 조건이 아니다.** 위치만 바뀌었다.
- **모바일(`md` 미만)에는 사이드바가 없다.** 그대로 두면 투표에 닿을 방법이 사라지므로, 모바일에서만 같은 패널을 본문 상단(탭 아래)에 렌더한다. CSS(`hidden md:block` / `md:hidden`)로 **항상 한쪽만 표시**되므로 보조기술에도 하나만 노출된다.

**구현 — 레이아웃은 자리만 내주고 내용은 토론방이 채운다.** 레이아웃이 `room/` 컴포넌트를 직접 import 하면 기능 간 교차 import(불문율 #7)가 된다. 그래서 `RedditLayout` 은 토론방 라우트에서 빈 `<div id="rnb-slot">` 만 렌더하고, `DebateRoom` 이 `createPortal` 로 `ThreadPanel` 을 그 자리에 그린다.

- 의존 방향이 **페이지 → 레이아웃** 한쪽으로만 흐른다. 슬롯 id 는 `src/lib/layoutSlots.ts` 에 둔다(컴포넌트가 아닌 상수라 공용 위치가 맞다).
- **추가 조회가 없다.** 패널은 `DebateRoom` 이 이미 받아둔 `GET /api/v2/room` 데이터를 props 로 받는다 — 탭·패널·대화가 같은 응답을 보므로 투표 직후에도 수치가 어긋나지 않는다.
- 스토어를 쓰지 않는다. portal 로 같은 React 트리에 남아 props 가 그대로 내려간다.

### 6.4 모바일 내비게이션 — 하단 탭 → 상단 햄버거 + 전체화면 모달

**문제**: 모바일(`lg` 미만)에서 LNB 가 **화면 하단 고정 탭**(`BottomNav`, `h-16`)으로 내려온다. 이 때문에:
1. 본문이 `pb-20` 을 깔아야 해서 **세로 공간을 80px 잃는다.** 토론방처럼 높이를 꽉 쓰는 화면에 그대로 손해다(§6.1 의 높이 계산에 `9.5rem` 이 들어간 이유).
2. 채팅 입력창과 하단 탭이 **화면 아래쪽에서 경쟁**한다. 키보드가 올라오면 더 나빠진다.
3. 항목이 3개(홈 · 이슈맵 · 앱 다운로드)뿐이라 화면 한 줄을 상시 점유할 만큼의 밀도가 아니다.

**결정**: 하단 탭을 없애고 **상단 바 우측, 프로필 아이콘 오른쪽에 햄버거 아이콘**을 둔다. 누르면 **화면을 전부 채우는 모달**로 메뉴를 연다.

```
┌──────────────────────────────┐
│ 토론철              (👤) (☰) │  ← 상단 바. 햄버거는 프로필 오른쪽
├──────────────────────────────┤
│                              │
│         (본문 — pb 해제)      │
│                              │
└──────────────────────────────┘

      ☰ 탭 →   ┌────────────────────┐
               │                (✕) │  ← 전체화면 모달
               │  홈                 │
               │  이슈맵              │
               │  앱 다운로드          │
               │                    │
               └────────────────────┘
```

- **노출 범위**: `lg` 미만에서만. `lg` 이상은 좌측 LNB 가 그대로 있으므로 햄버거를 숨긴다.
- **위치**: 프로필 아이콘의 **오른쪽**. 비로그인 상태에서는 프로필 자리에 로그인 버튼이 있으므로 **로그인 버튼 오른쪽**이 된다.
- **모달**: `fixed inset-0`, 화면 전체. 배경 반투명이 아니라 **불투명 surface** — "메뉴 화면"으로 읽혀야 한다.
- 닫기: 우측 상단 ✕ · ESC · 메뉴 항목 선택. 열려 있는 동안 `document.body.style.overflow = "hidden"` (기존 `AppDownloadModal` 과 동일 패턴).
- 현재 활성 메뉴는 좌측 LNB 와 같은 규칙으로 표시한다(`pathname === href` → brand 색).
- 항목은 `PUBLIC_NAV_ITEMS` + 앱 다운로드로 **좌측 LNB 와 동일한 목록**을 쓴다. 두 곳이 갈라지지 않도록 상수를 공유한다.
- **부수 효과 — 높이 계산이 단순해진다.** `main` 의 `pb-20 lg:pb-4` 가 `pb-4` 로 통일되고, `DebateRoom` 의 `h-[calc(100dvh-9.5rem)] lg:h-[calc(100dvh-5.5rem)]` 도 **한 값으로 합쳐진다.** 모바일에서 대화 영역이 80px 늘어난다.
- 접근성: 버튼에 `aria-label="메뉴"`, `aria-expanded`, 모달에 `role="dialog"` · `aria-modal="true"`.

### 7.4 홈 "뜨겁게 논쟁 중인 찬반토론" 제거

`IssueCard` 가 쓰던 데이터가 **운영에서 항상 비어 있고**, 새 URL 도 만들 수 없어 섹션째 제거했다.

- `GET /api/v1/users/home` 은 `ListIssueBriefResponse`(이슈 배열)만 반환한다. `parseHome` 이 배열 분기를 타서 `chatRooms` 는 **항상 `[]`** → 섹션이 렌더된 적이 없다.
- `GET /api/v1/home/recommend` 의 `chatRoomResponse` 도 운영에서 빈 배열이고, 스키마(`ResponseWithTime`)에 **`issueId` 가 없다** → `threadHref` 를 만들 수 없다.
- "이런 토론은 어때요?"(`top5BestChatRooms`)는 `issueId` 가 있어 정상 동작한다. 이쪽은 유지.

### 11.3 스크롤바 통일 — 배포 완료 (`4ef3384`, 2026-08-19)

채팅 목록이 브라우저 기본 스크롤바를 쓰고 있었다. `.scrollbar-grey` 유틸이 이미 있었지만 `::-webkit-scrollbar` 에 `height` 만 있어 가로 전용이었고, 무엇보다 **채팅·좌우 사이드바·모달·페이지 스크롤바 어디에도 붙어 있지 않았다**. 붙이는 걸 잊는 게 본질이라 유틸을 지우고 `*` 전역 기본값으로 올렸다. `.scrollbar-none` 은 클래스 선택자라 전역값을 이기므로 탭 스트립의 막대 숨김(§6.1)은 그대로 남는다 — 잘린 탭 자체가 스크롤 힌트인 유일한 예외다.

| 파일 | 내용 |
|---|---|
| `src/app/globals.css` | `.scrollbar-grey` → `*` 전역 규칙 승격 |
| `src/components/room/ChatRoom.tsx` | 메시지 목록에 `overscroll-contain` + `pr-1` |
| `src/app/page.tsx` | 중복된 `.scrollbar-grey` 제거 2곳 |

> **폭 주의.** Chrome 121+ 는 `scrollbar-width` 가 지정되면 `::-webkit-scrollbar` 를 무시한다. 실제 폭은 브라우저의 thin 값(실측 11px)이고 webkit 규칙은 Safari 폴백으로만 동작한다. 6px 을 기대하고 여백을 계산하지 말 것.
