### 2.3 호환성 약속 (백엔드 → 웹/앱)

앱은 스토어 심사로 웹보다 며칠 늦게 반영된다. 그 기간 백엔드가 구버전 앱을 동시 지원한다.

- **응답 필드를 제거·개명·의미 변경하지 않는다.** 추가만 한다.
- **요청의 새 필드는 항상 optional.**
- 그래도 바꿔야 하면 `/api/v2/...` 로 신규 엔드포인트를 파고 기존 것을 유지한다.

**웹에 대한 함의: 새 구조를 먼저 개발해도 되고, 그동안 기존 API 는 계속 동작한다.** 초판 §8 이 요청했던 `ChatRoomResponse.agree/disagree/opinion` **제거 요청은 철회한다** — 백엔드는 이 필드를 **대표 주제 기준으로 계속 채운다**(§4.3). 웹은 읽지 않으면 된다.

## 3. 도메인 모델

```
이슈 (Issue)                        ← 최상위. ADMIN 생성.
└── 채팅방 (ChatRoom) [*]           ← 이슈당 N개. ADMIN 생성. 상시 개방, 투표 불필요.
     ├── 일반 발언                  topic_id = NULL
     └── 토론 주제 (DebateTopic) [*] ← 유저 생성. 0개 가능. ★ 찬반이 여기 붙는다.
          ├── 스레드 발언            topic_id = N
          ├── 토론위키 (DebateWiki)  주제 1건 = 위키 1장
          └── 찬반 (UserTopicOpinion)
```

### 3.1 각 개념

**채팅방** — 이슈에 직접 붙는다. **ADMIN 만 생성**하므로 난립하지 않는다. 초판이 미결로 남겼던 "채팅방 분할 기준"은 **권한으로 해소**되었다. 프론트는 여전히 **목록으로 렌더**한다(이슈당 1개를 가정하지 않는다).

**토론 주제 (DebateTopic)** — 채팅 중 토론 주제가 발생하면 **유저가 만든다.** `OPEN` → `CLOSED` 로 전이. **찬반 투표가 붙는 유일한 층위.**

**토론위키 (DebateWiki)** — 주제와 **1:1**. 주제가 열리면 위키 1장이 생기고, 주제가 닫히면 아카이브된다. 이슈에는 주제 수만큼 위키가 쌓인다. 기존 "토론방 화면"(`RoomDetail`)이 이 위키 화면으로 대체된다.

### 3.2 상태 전이

```
[채팅 중 토론 주제 발생]
        │  유저가 주제 생성
        ▼
   DebateTopic(OPEN) ──1:1── DebateWiki(ACTIVE)
        │                        │ 유저가 본문 편집
        │                        │ 찬반 게이지 = 주제 투표 집계
        │  무활동 7일 자동 종료, 또는 ADMIN 수동 종료
        │  (작성자는 닫을 수 없음)
        ▼                        ▼
   DebateTopic(CLOSED) ────  DebateWiki(ARCHIVED)
        · 새 발언 불가 (읽기 전용)      · 편집 잠금, 최종 찬반 결과 고정
        · 투표 마감 (기존 표 보존·조회 가능)
```

- **단일 진실 공급원은 `DebateTopic.status`.** 위키 상태는 파생값.
- 한 채팅방에 동시 `OPEN` 주제는 **복수 허용**. 상한을 서버에 걸지 않는다 — 채팅방 상단 스트립에서 **최근 3개 + 가로 스크롤**로 표현만 제한한다.

### 3.3 찬반 투표의 이동

| | v0.7 (현행) | v0.7.1 |
|---|---|---|
| 투표 대상 | 채팅방 | **토론 주제** |
| 투표 시점 | 입장 **전** (강제) | 주제 참여 시 (선택) |
| 미투표 시 | 채팅 입장 불가 | **채팅 자유 참여.** 주제 열람·발언도 가능, 투표만 안 된 상태 |
| 미투표 표현 | — | **행 없음 = NEUTRAL** (`NEUTRAL` 을 저장하지 않는다) |
| API | `POST /room/vote` | 주제 단위 투표 API (스펙 대기) |

## 4. 백엔드 데이터 구조 (v1.3.4 설계 — 프론트가 전제하는 형태)

> ⚠️ **불문율 #1**: 아래는 백엔드 v1.3.4 PRD 의 설계이며 **API 응답 스펙이 확정된 것이 아니다.**
> 백엔드가 스펙을 공유한 뒤 실제 `curl` 로 확인하기 전까지 `src/lib/api/*.ts` 에 타입을 커밋하지 않는다.

### 4.1 신규 테이블 (참고용 — 응답 필드명은 별개)

```
debate_topic          topic_id, chat_room_id, issue_id(비정규화), title,
                      status(OPEN/CLOSED), opened_at, closed_at,
                      agree_count, disagree_count, created_by
user_topic_opinion    user_id, topic_id, opinion(AGREE/DISAGREE)
                      UNIQUE(user_id, topic_id) — NEUTRAL 미저장
debate_wiki           wiki_id, topic_id(1:1), status(ACTIVE/ARCHIVED/HIDDEN),
                      current_revision_id
debate_wiki_revision  revision_id, wiki_id, content, edited_by, edit_summary
chat                  + topic_id (nullable)
chat_room             + default_topic_id  ← 대표 주제 shim
```

### 4.2 스레드 조회 두 모드

| 모드 | 용도 | 웹 |
|---|---|---|
| 전체 스트림 | 채팅방 기본 화면. 스레드 발언도 인라인으로 함께 보이고 소속 주제 배지를 단다 | **기존 조회 경로 그대로** — 무회귀 |
| 스레드 필터 | 특정 주제만 골라 보기 | 신규 |

- **커서는 모드별로 독립**이다. 전체 스트림 커서를 스레드 뷰에 재사용하면 페이지가 어긋난다. 웹도 커서 상태를 모드별로 분리 보관한다.

### 4.3 대표 주제(default topic) shim — 구버전 앱 호환

마이그레이션에서 채팅방마다 "첫 주제"를 만들어 **대표 주제**로 지정한다(`chat_room.default_topic_id`).

- 구 API `POST /api/v1/room/vote` → 그 방의 **대표 주제에 투표**하는 것으로 라우팅
- 구 API `GET /api/v1/room` 의 `agree`/`disagree`/`opinion` → **대표 주제 기준**으로 계속 채워짐

**웹에 대한 함의**: 신규 투표 API 로 갈아타기 전까지 `src/lib/api/room.ts:46` 의 `voteRoom()` 은 **그대로 동작한다.** 전환을 서두를 필요가 없다.

> 확인 필요(§9-4): 대표 주제가 CLOSED 되면 구 앱 투표가 어디로 가는가. 백엔드 PRD 권장안은 **(c) 대표 주제를 자동 종료 대상에서 제외**.

### 4.4 `opinionType` — 서버 판정 + 발언 시점 고정

현재 웹은 메시지 전송 시 `opinionType` 을 **클라이언트 값으로 실어 보낸다**(`src/components/room/ChatRoom.tsx:235`, `src/lib/api/chatSocket.ts:168`). 백엔드는 이를 **서버 판정**으로 바꾼다.

```
메시지의 topic_id == NULL          → 배지 없음
메시지의 topic_id == N
   ├ 해당 주제에 투표 있음          → 그 값 (AGREE / DISAGREE)
   └ 없음                         → 배지 없음
```

- **발언 시점에 고정(snapshot)한다.** 나중에 입장을 바꿔도 과거 발언의 배지는 그대로다. (실시간 반영이면 "찬성합니다"라는 메시지에 [반대] 배지가 붙는 로그가 만들어진다)
- **웹 작업**: `opinionType` 전송을 제거한다. 시점은 §9-5 확인 후.
- `src/lib/api/chatSocket.ts:161` 의 "클라이언트 값을 사용한다" 주석도 함께 정리.

## 5. 화면 IA

### 5.1 라우트

| 라우트 | v0.7 | v0.7.1 |
|---|---|---|
| `/issue/[id]/[slug]` | 이슈 상세 (토론방 목록) | 이슈 상세 — **채팅방 목록 + 지난 토론(위키) 목록** |
| `/issue/[id]/[slug]/[roomId]/[roomSlug]` | 토론방(찬반+입장) | **토론위키 문서** (`wikiId` 기준) |
| `/issue/[id]/[slug]/wiki` | — | **신규** — 이슈의 위키 문서 목록 |
| `/issue/[id]/[slug]/chat/[roomId]/[roomSlug]` | — | **신규** — 이슈 하위 채팅방 |
| `/room/[id]` | 토론방 (raw id) | **채팅방으로 리다이렉트** (홈 카드·앱 딥링크 호환) |
| `/room/[id]/chat` | 채팅 | 유지 (raw roomId 진입 경로) |

- 이슈당 채팅방이 N개이므로 채팅 라우트에 `roomId` 세그먼트가 필요하다. `/issue/[id]/[slug]/chat` 형태는 쓰지 않는다.
- 세그먼트는 `src/lib/slug.ts` 의 base36 + slug 규칙을 그대로 따른다.
- `roomHref()` (`src/lib/slug.ts:34`) 는 **채팅방 경로로 의미를 유지**하고, 위키용 `wikiHref(issueId, issueTitle, wikiId, wikiTitle)` 를 신설한다.

> **위키 목록은 이슈 단위로 묶는다.** 주제는 채팅방에 속하지만 유저 관점의 산출물은 이슈의 것이다. → 백엔드에 `debate_topic.issue_id` 비정규화가 필요하다고 전달 완료.

```
┌ 채팅방 헤더  (이슈 헤더 확장은 v0.7.2)
├ 진행 중인 토론 ──────────── (가로 스크롤, 최대 3)
│  [진행 중] 계엄은 위헌인가   62:38  →
│  [진행 중] 국회 대응은 적절  41:59  →
│  [+ 토론 주제 만들기]                      ← 유저 생성 (신규)
├ ─────────────────────────────────
│  (메시지 목록 — v0.7 렌더 유지: 아바타/커뮤니티/닉네임/의견/시간)
│  · 스레드 발언은 소속 주제 배지 + 위키 링크
├ ─────────────────────────────────
└ [입력창]  — 로그인만 필요. 투표 불필요.
```

- **주제가 0개면 스트립 영역 전체를 감춘다.** 빈 배열은 정상이며 에러가 아니다(§2.2-5). "토론 주제 만들기" CTA 만 남긴다.
- 주제 카드 탭 → 해당 **위키 문서**로 이동.

### 5.4 토론위키 문서 (기존 토론방 화면 대체)

```
┌ 위키 헤더
│  [진행 중] 쟁점 제목
│  소속 이슈: 윤석열 계엄  ·  시작 12/04 21:10  ·  7일 무활동 시 자동 종료
├ 찬반 게이지 (DeVoteGauge) — 주제 투표 집계
│  [ 찬성 62% ]————[ 38% 반대 ]   [찬성] [반대]  ← 미투표도 열람 가능
├ 본문
│  (문서 전체 — 편집 시 리비전 1건 생성)
│                                       [편집]
├ [ 채팅방에서 이어 말하기 ]  → 해당 스레드로 진입
└ 편집 이력 (접힘) — 편집자 · 시각 · 요약
```

**아카이브 상태**에서는 편집 버튼과 투표 버튼을 감추고, "종료된 토론입니다 · 새 주제 열기" 안내를 노출한다.

## 6. 확인 대기 중인 설계 결정 3건

백엔드 스펙 공유 시 확정된다. **아래 "잠정 전제"로 개발을 시작하되, 확정 전까지 해당 컴포넌트는 확정 리스크를 안고 있다.**

### 6.1 위키 편집 단위 — **잠정: 문서 전체 리비전**

| | 초판 안 | 백엔드 v1.3.4 설계 |
|---|---|---|
| 단위 | 문단(block) 단위 + 문단 락 | **문서 전체 리비전** (`content` 단일 컬럼) |
| 메타 | 문단별 `origin: AI\|USER`, `editorCount` | `edited_by`, `edit_summary` |

**잠정 전제: 백엔드 안(문서 리비전).** 문단 락은 동시 편집이 실제로 발생할 때 의미가 있는데, 현재 규모(prod `chat` 386행 / `users` 231명)에서 한 위키를 두 사람이 동시에 편집할 확률은 사실상 0이다. 리비전 구조는 나중에 문단으로 쪼갤 수 있다.

→ 초판 §7.2 의 `WikiBlockEditor.tsx` 는 **범위에서 제외**. `WikiDocument.tsx` 가 문서 전체 편집을 담당한다.

### 6.2 AI 초안 — **잠정: 없음**

초판 §4.1 은 "주제 생성 즉시 AI 초안 생성"을 **빈 위키 회피 수단**으로 넣었으나, 백엔드 v1.3.4 설계에는 이 개념이 없다.

**잠정 전제: AI 초안 없이 간다.** 대신 웹이 빈 상태를 UX 로 처리한다:
- 주제 생성 시 **제목과 승격 대상 발언을 첫 리비전에 자동으로 채운다**
- 본문이 비었을 때 "첫 문단을 작성해보세요" CTA + 작성 예시(쟁점 / 찬성 논거 / 반대 논거) 템플릿 제공

→ AI 초안은 나중에 리비전 구조 위에 얹으면 되므로 **스키마 변경 없이 추가 가능**하다.

### 6.3 위키 편집 권한 — **잠정: ADMIN + 주제 작성자**

백엔드 권한 매트릭스는 일반 USER 개방 여부를 "정책 결정 필요"로 열어두었고, 초기값을 **ADMIN + 주제 작성자**로 좁게 제안한다.

**잠정 전제: 좁게 시작.** 되돌리기 기능이 없는 동안 개방 범위는 좁게 두고 넓히는 것이 정석이며, 리비전이 있으니 나중에 개방해도 스키마가 바뀌지 않는다.

> ⚠️ **제품 관점의 부작용**: 이러면 "위키"가 아니라 사실상 **"작성자의 글"** 이 된다. 집단 편집이 이 기능의 핵심 가치라면 개방 범위를 넓혀야 하고, 그때는 되돌리기·편집 잠금·훼손 대응이 세트로 필요하다. **기획 판단 필요.**

## 8. 마이그레이션

이슈당 채팅방이 N개로 유지되므로 **기존 채팅방을 통폐합하지 않는다.**

| 항목 | 처리 |
|---|---|
| 기존 채팅방 | **그대로 유지.** 노출 방식만 바뀐다 |
| 기존 `room/vote` 투표 데이터 | 백엔드가 대표 주제로 이관한다(§4.3). 웹은 관여하지 않음 |
| `POST /api/v1/room/vote` | **당장 중단하지 않는다.** 대표 주제 shim 이 계속 커버하므로 신규 투표 API 전환을 서두를 필요가 없다 |
| `ChatRoomResponse.agree/disagree/opinion` | **제거 요청 철회.** 대표 주제 기준으로 계속 채워진다. 웹은 읽지 않는다 |
| `/room/[id]`, `/room/[id]/chat` | 유지 + 리다이렉트 (홈 추천 카드·앱 딥링크 호환) |
| 모바일 앱 | 스토어 심사로 웹보다 며칠 늦다. **백엔드 호환성 약속(§2.3)이 이 구간을 커버**하므로 웹이 먼저 배포해도 된다 |

**배포 순서**
1. 백엔드 v1.3.4 배포 (기존 엔드포인트 유지, 추가만)
2. 웹 v0.7.1 배포 ← **앱을 기다리지 않아도 된다**
3. 앱 v1.3.4 대응 릴리스
4. 구버전 앱 사용률이 떨어진 뒤 레거시 정리 (백엔드 Contract 단계)
