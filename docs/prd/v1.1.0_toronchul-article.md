## 0. 한 줄 정의

**이슈 페이지가 "토론 주제 목록" 에서 "이 이슈에 무슨 일이 있었고, 토론철은 그것을 어떻게 정리했나" 로 바뀐다.** 아티클은 그 정리를 담는 **독립 문서**다.

```
이슈: 도널드 트럼프 2기 행정부                    /issue/8
├ 토론위키 (v1.0.0)          — 배경·쟁점·찬반 논거, 이슈당 1장
├ ★ 사건 타임라인            — 시간 역순
│   ├ 2026-04-02  상호관세 발표
│   │    "미국이 …을 발표했다. …"   ← 사건 설명 = 관련 아티클 요약 인용
│   │    토론철 아티클 2편 →           ← /article/{b36} 로 이동
│   └ 2026-01-20  2기 취임
└ 토론 주제                  — 기존

아티클: /article/{b36}       ← 이슈·사건 아래에 있지 않다. 어느 이슈·사건에서든 이 한 URL 로 온다
```

### 0.1 관계 — 아티클은 종속되지 않는다 (2026-10-19 결정)

| 관계 | 내용 |
|---|---|
| **아티클 ↔ 사건** | N:M (데이터 `toronchul_article_event`). 사건은 아티클을 **가리킬 뿐** 소유하지 않는다 |
| **아티클 ↔ 이슈** | 사건을 거쳐 이어진다. 아티클 한 편이 여러 사건·여러 이슈에 걸칠 수 있다 |
| **URL** | `/article/{b36}` — 이슈·사건이 경로에 없다. v0.9.0 §4.3c(평평한 엔티티 디렉터리)와 같은 이유: 상위가 경로에 있으면 상위가 둘 이상일 때 URL 이 둘이 되고, 소속이 바뀌면 URL 이 바뀐다 |
| **이동** | 이슈 페이지 → 사건 타임라인 → 사건의 관련 아티클 → 아티클 본문 페이지. 아티클 페이지에서는 관련 사건(이슈 페이지의 해당 사건 앵커)으로 되돌아간다 |
| **참조** | 타임라인이 사건을 설명할 때 **아티클 내용 일부(요약)를 인용**한다. 원문은 아티클 페이지 한 곳에만 있고 타임라인은 발췌 + 링크다 → 중복 콘텐츠가 아니라 인용이며, 정식 위치(canonical)는 아티클 페이지다 |

## 1. 왜 이 순서인가

| 질문 | 답할 수 있는 콘텐츠 | 버전 |
|---|---|---|
| "이 이슈가 뭔가?" | 토론위키 | v1.0.0 |
| **"요즘 이 이슈에 무슨 일이 있었나?"** | **사건 타임라인 + 아티클** | **v1.1.0** |
| "사람들은 어떻게 생각하나?" | 토론 주제 찬반 · (채팅) | v0.7 ~ |

위키는 정적인 백과사전이고 갱신이 드물다. **사건과 아티클은 최신성을 준다.** v0.9.0 §2 의 "사건 = 실시간성 + 맥락" 이 이 버전에서 실제로 들어온다. 아티클은 동시에 토론철의 1차 데이터(찬반 수치·참여 커뮤니티 분포)를 인용하는 **자체 발행 글**이라 GEO 상 Cite Sources·Statistics 가 자연스럽게 붙는다(v0.9.0 §5.4).

## 2. 토론철 아티클

### 2.1 URL · 렌더

- **`/article/{b36}`** — 기사 PK(`toronchul_article.id`, BIGINT AUTO_INCREMENT — 데이터 v0.11.0 §6)의 소문자 base36. v0.9.0 스킴 그대로, 슬러그 없음
- 서버 렌더. 판정 규칙은 v0.9.0 §4.3d (대문자 308 · 별칭 404 · 없는 id 404). **발행 상태(`PUBLISHED`)가 아니면 404**
- `src/lib/routes.ts` 에 `articleHref(articleId)` 추가

### 2.2 화면

```
[토론철 AI 작성 · 운영진 검수]                      ← 상단 라벨 (필수)
미국 상호관세 발표, 토론철 이용자 72% "중단해야"       H1 제목
2026-04-03 발행 · 2026-04-03 수정

(요약 2~3문장)
(본문)

토론철 데이터                                       ← 1차 데이터 블록
  관련 토론 주제 · 찬반 수치 · 참여 커뮤니티 → /debate/{b36}

출처                                                ← 원문 기사 링크 목록
관련 사건                                           ← 사건마다 "{이슈 제목} · {사건 제목}" → /issue/{b36}#event-{b36}
```

> 상단에 "← 이슈" 뒤로가기를 두지 않는다. 아티클은 이슈 아래가 아니고, 여러 이슈에 걸칠 수 있다. 관계는 하단 "관련 사건" 이 맡는다.

### 2.3 발행 게이트 — 웹 노출 전 필수

v0.9.0 §5.4 와 `seo-geo` 스킬 `references/ai-news.md` 의 게이트를 이 버전의 **착수 조건**으로 삼는다. scaled content abuse 판정은 **도메인 전체**에 걸려 이슈·토론 페이지까지 같이 떨어진다.

| 게이트 | 상태 |
|---|---|
| 발행 전 **사람 검수** | ✅ 데이터 v0.11.0 §1 이 설계에 넣었다 — 자동 발행 없음, `APPROVED → PUBLISHED` 는 사람 또는 예약 |
| **AI 생성 명시** — 화면 상단 라벨 + `NewsArticle.creditText` | 웹 몫 (§2.2) |
| **가상의 기자 이름 금지** — `author`·`publisher` 는 조직(토론철) | 웹 몫 |
| **발행량을 검수 역량에 연동** | 데이터 v0.11.0 은 "하루 수십 건" 규모. 그 이상으로 늘릴 때 재검토 |
| **토론철 1차 데이터 근거** — 외부 기사 리라이트 금지 | 데이터 v0.11.0 §4(저작권: 원문 복제 검사) + 웹의 "토론철 데이터" 블록 |
| **인터넷신문 등록 여부** | ⏳ 미확인. 등록 전에는 아래 robots 정책 |

**하나라도 미충족이면 `/article/` 을 robots.txt Disallow 로 두고 시작한다.** 색인은 나중에 켤 수 있지만 판정은 회복에 수개월이 걸린다.

### 2.4 구조화 데이터 · sitemap

- `NewsArticle` + `BreadcrumbList`(**홈 › 기사 제목** — 아티클은 이슈 아래가 아니다. 아티클 목록 페이지 `/article` 을 열면 홈 › 토론철 아티클 › 제목) + `about` → 관련 이슈들(복수 가능). `datePublished` = 발행 시각(`date_published`), `dateModified` = 마지막 리비전. `creditText` 에 AI 생성·검수 문구
- `isBasedOn` / `citation` 으로 출처 기사
- sitemap: 발행 기사만. 기사가 하루 수십 건이면 1년에 약 1만 URL — 단일 파일 한도(5만) 안이다. 넘어갈 때 `generateSitemaps` 로 샤딩(시그니처는 v0.9.0 §6.2 에 고정)

## 3. 사건 타임라인 (이슈 페이지)

v1.x.0 문서 §2 에서 옮겨 왔다. 사건은 이슈 안에서 일어난 사실 단위이고 **읽기 전용**이다(온톨로지가 제안하고 사람이 승인 — 데이터 v0.10.0).

- 이슈 상세에 **사건 섹션**: 발생 시각 내림차순 타임라인. 사건 카드 = 제목 · 발생 시각 · **사건 설명** · 관련 아티클 링크
- **사건 설명은 관련 아티클의 요약을 인용한다** — 아티클이 여러 편이면 가장 최근 발행본. 인용임을 화면에 보이게 하고(따옴표·"토론철 아티클" 표기) 아티클로 링크한다. 아티클이 없는 사건은 사건 자체 요약(있으면)만, 그것도 없으면 제목·시각만
  - 그대로 쓸 수 있는지(길이·평문 여부·독립적으로 읽히는 문장인지)는 데이터 세션에 확인 중 → §4.1
- 사건이 소유하는 것은 **미디어·아티클 묶음뿐** — 채팅방이나 위키를 갖지 않는다(v1.x.0 원문 결정 유지)
- **서버 렌더.** 사건 목록은 크롤러가 읽는 "최신성" 본문이다
- **사건 상세 페이지 `/event/{b36}` 은 이 버전에서 열지 않는다.** v0.9.0 이 URL 자리만 예약했다. 사건 하나에 제목·시각·요약 몇 줄뿐이면 얇은 페이지가 사건 수만큼 생긴다. 사건마다 아티클이 쌓여 **페이지당 고유 본문이 생긴 뒤** 연다. 그때까지 사건은 이슈 페이지 안의 앵커(`/issue/{b36}#event-{b36}`)로만 가리킨다
- 커서 페이징 전제로 받는다 — 사건 생성이 자동화(온톨로지)되면 이슈당 건수가 크게 늘 수 있다

## 4. 데이터 현황 · 백엔드에 요청할 것

### 4.1 데이터 세션 확인 (2026-10-19, `toronchul_data_v1` cf00e38 기준)

**운영 DB 에 `toronchul_article` 테이블이 아직 없다. PUBLISHED 0건, 운영 사건(`news_event`)도 0건**(사건은 Discord 승인 후 생성 — 승인 0건). 있는 것은 로컬 후보 JSON(토론철판 9편, 상태 REVIEW)뿐이다. 데이터 v0.11.0 §6 스키마는 제안 단계이고 테이블명(D1)·백엔드 반영이 미정이다.

→ **웹은 아래 필드를 타입으로 고정하지 않는다**(불문율 #1). 백엔드 공개 API 의 Swagger 가 나오면 그걸로 맞춘다. 아래는 그 요청의 근거다.

| 후보 JSON 필드 | 의미 · 웹 용도 |
|---|---|
| `headline` | H1 · `NewsArticle.headline` |
| `summary` | **평문, 2~3문장, 97~145자(평균 128자).** 기사 없이 읽어도 문맥이 서는 독립 문장, "이 기사는…" 류 메타 문장 금지(기자 원칙 + 형식 검사). **사건 타임라인 카드에 그대로 써도 되는 품질** — 단 (a) **`edition = toronchul` 판만**(티머니GO판은 1~2문장 축약), (b) **PUBLISHED 만** |
| `body` | `[{ text, sources: [media_id] }]` **문단 배열, 문단마다 평문.** 소제목·목록·표·링크·Markdown 없음, 인용은 문장 안 따옴표뿐. 4~6문단, 700~1,800자. 문단별 `sources` 는 근거 검사용 내부 값 — 응답에 내지 않는다 → **웹은 Markdown 렌더러 없이 `<p>` 로 그린다** |
| `byline` | `"토론철 AI 기자"` 고정, 사람 이름 없음(AI기본법 제31조, `ai_generated = true`) → 화면 "토론철 AI 기자 · AI 생성 기사", JSON-LD `author` = Organization 토론철 (웹 방침과 일치) |
| `issue_ids` | **정수 배열, 앱 `issue.id`.** 아티클↔이슈는 사건을 거친 M:N(현재 9편 중 1편만 이슈 있음). 데이터 PRD 의 `issue_id VARCHAR(36)` 단일 컬럼은 옛 초안의 잔재 — 빼고 사건 연결로 이슈를 얻는 쪽으로 제안 예정 |
| `event_id` | 지금은 아티클 1편 = 사건 1개. 로컬 id(`"20261018-019"`)이고 운영 `news_event.id` 가 아니다. 테이블은 N:M(`toronchul_article_event`)로 확장 대비 |
| `source_ids` | 운영 `media.id` → `media` 의 `title`·`media`(매체명)·`url` 로 원문 정보를 얻을 수 있다. **노출 여부는 D7(법률 검토)과 함께 미정** |
| `date_published`·`view_count`·운영 id | 아직 없음(발행 시점에 생김) |
| `image_url` | v0.11.0 은 이미지를 제공하지 않는다 |

사건의 운영 정본은 백엔드 `news_event` / `issue_news_event`(사건↔이슈 M:N) / `news_event_media`(PR #213·#216) — 컬럼은 백엔드에서 받는다.

### 4.2 백엔드에 요청할 것

| # | 요청 | 비고 |
|---|---|---|
| A-1 | **아티클 단건 공개 조회** — 익명 200, PUBLISHED 가 아니거나 없는 id 는 404. `headline`·`summary`·`body`(문단 텍스트 배열, 문단별 sources 제외)·`byline`·`aiGenerated`·`articleSection`·`keywords`·`datePublished`·`updatedAt`(마지막 리비전)·관련 사건 `[{eventId, name, date, issueIds}]` | **toronchul 판만** 내려 주는 공개 경로 |
| A-2 | **이슈 사건 타임라인 공개 조회** — `GET` 이슈별, 발생 시각 내림차순, 커서 페이징. 사건마다 `eventId`·`name`·`date`·관련 PUBLISHED 아티클 `[{articleId, headline, summary, datePublished}]`(최신 발행순) | 사건 카드의 설명 = 첫 아티클 `summary`(§3) |
| A-3 | **아티클 사이트맵 피드** — `GET /api/v1/sitemap/articles` (#217 과 같은 형태: `items[{articleId, updatedAt}]`, `nextCursor`) | lastmod |
| A-4 | (D7 결정 후) 아티클 출처 `[{title, outlet, url}]` | 노출이 정해지면 |

> 고객사(티머니) API 와는 별개다. 그쪽은 인증·미터링·민감도 필터가 붙는 B2B 경로이고(데이터 v0.11.0 §5), 웹은 **공개 읽기** 경로가 필요하다. 같은 테이블을 읽되 엔드포인트를 섞지 않는다 — 미터링 경로에 크롤러 트래픽이 섞이면 과금 집계가 오염된다. 웹 서버발 호출은 #218 웹 키 버킷으로 들어간다.

### 4.3 화면에 미치는 것 (확인 결과 반영)

- 아티클 본문은 **Markdown 렌더러를 쓰지 않는다** — 문단 배열을 `<p>` 로. 위키(v1.0.0)와 다르다
- 상단 라벨 "토론철 AI 기자 · AI 생성 기사", `creditText` 같은 문구
- 출처 블록(§2.2)은 **D7 결정 전까지 그리지 않는다.** 대신 1차 데이터 블록(관련 토론 찬반)은 그린다 — GEO 의 근거 제시는 그쪽이 맡는다
